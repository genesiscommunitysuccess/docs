A class-based, annotation-driven way to write event handlers, as an alternative to [GPAL `.kts` event handlers](/develop/server-capabilities/core-business-logic-event-handler).

:::caution
`genesis-eventhandler-spring-boot-starter` is still work-in-progress upstream — expect its API and the set of supported annotations to change as the module matures. The gaps below are accurate as of this writing, but check back before relying on any of them being fixed.
:::

## Overview

`genesis-eventhandler-spring-boot-starter` lets a Spring Boot application define Genesis event handlers as plain annotated Kotlin or Java classes, instead of writing `.kts` GPAL event-handler scripts. A class annotated `@GenesisEventHandler("EVENT_NAME")` (or `@GenesisEventController` for a group of related events), with `@EventValidate`/`@EventCommit`-annotated methods, is scanned at Spring context start-up and registered into the same `TypedEventManager` registry as GPAL's compiled and scripted event handlers.

From the router's or a connecting client's point of view, an event served by one of these Spring beans looks identical to one served by a GPAL handler, and both mechanisms can coexist in the same process.

This module builds on the [Spring application core](../core) and depends on `genesis-eventhandler` and `genesis-jpa-base`. Handler payloads and validate/commit logic will often touch JPA entities from [JPA data access](../jpa-data-access).

Choose this module when the surrounding process is already a Spring Boot / JPA application and staying in that programming model outweighs GPAL's greater maturity. It's a second, parallel authoring style for the same event-handler concept, not a replacement — GPAL (`genesis-pal-eventhandler`, `.kts` scripts, `GPalEventHandler`) remains the default for core business logic today.

Exposing an HTTP surface (`@RestController`) through the Genesis router is **not** part of this module — that lives in the [Spring application core](../core).

## Getting set up

Add a dependency on `genesis-eventhandler-spring-boot-starter`; `genesis-spring-boot-starter`, `genesis-eventhandler` and `genesis-jpa-base` come transitively. There is no separate annotation-processing or KSP step for this module — annotations are read via runtime reflection when a bean is post-processed, not at compile time.

```kotlin
plugins {
    id("global.genesis.spring")
}

dependencies {
    api("global.genesis:genesis-eventhandler-spring-boot-starter")
}
```

The module ships its own Spring Boot auto-configuration (`GenesisSpringEventHandlerConfig`), so adding the dependency and annotating a `@Component` bean is enough — there's nothing to `@Import` manually. That configuration does expect `RightSummaryCache`, `TypedEventManager`, `MetaDataRegistry`, `ServiceRegistry` and `ServiceDiscovery` to already be in the Spring context — the [Spring application core](../core)'s own auto-configuration supplies all of these, so set that up first and there's nothing extra to wire in.

:::note
This includes logging: Genesis Spring integration only supports **Logback**, not the Log4j2 backend
used elsewhere in Genesis. See [Application core: Set-up](../core#set-up) for what this requires, or
[Getting started: Step 3](../getting-started#step-3-switch-logging-to-logback) for the three-file
change.
:::

A handler class doesn't need its own `@Component` — `@GenesisEventHandler`, `@GenesisEventController` and `@EventControllerAdvice` are themselves meta-annotated `@Component`, so Spring's component scan picks a class up as soon as it carries one of them. Constructor-inject whatever the handler needs (a repository, `RxDb`, `EventProvider`, and so on) the normal Spring way.

One hard constraint to plan around from the start: **never model an event payload or handler class as a Java `record`.** Doing so crashes bean creation with `Can't compute ClassId for primitive type: int`, thrown from Kotlin reflection while the module inspects the record's constructor. Use a Kotlin `data class`, or an ordinary Java class with a no-arg constructor and getters/setters, instead.

## Example configuration

The smallest realistic handler is a single event with a commit phase only — no validation, no rights. A payload parameter with no annotation is bound automatically to the incoming event details:

<Tabs defaultValue="kotlin" values={[{ label: 'Kotlin', value: 'kotlin', }, { label: 'Java', value: 'java', }]}>
<TabItem value="kotlin">

```kotlin
import global.genesis.eventhandler.spring.annotation.EventCommit
import global.genesis.eventhandler.spring.annotation.GenesisEventHandler

data class Update(
    val name: String = "",
    val qty: Int = 0,
)

@GenesisEventHandler("TOUCH")
class CommitOnlyEventHandler {

    @EventCommit
    fun commit(details: Update) {
        // ... do the work
    }
}
```

</TabItem>

`@GenesisEventHandler("TOUCH")` registers the event with `TypedEventManager` under that name, the same registry a GPAL handler uses. The event name must match `[A-Z][A-Z0-9_]+`, or registration fails at start-up. A `commit` method returning `Unit`/`void` (as above) maps to an empty `EventReply.EventAck`; returning a domain object instead wraps it as `EventAck(generated = listOf(thatObject))`, and returning a `List<*>` uses the list directly as `generated`.

Most handlers need both a validation phase and a commit phase — the equivalent of GPAL's `onValidate`/`onCommit` split. The value returned by `@EventValidate` becomes the "context" available to `@EventCommit`, injected via a parameter annotated `@EventContext` (or implicitly, if the parameter's type already matches). The two mechanisms aren't exclusive: a validating handler can also constructor-inject collaborators like `EventProvider` (see [Triggering other events](#triggering-other-events) below) and use them from `@EventCommit` alongside the injected context:

<Tabs defaultValue="kotlin" values={[{ label: 'Kotlin', value: 'kotlin', }, { label: 'Java', value: 'java', }]}>
<TabItem value="kotlin">

```kotlin
import global.genesis.eventhandler.spring.annotation.EventCommit
import global.genesis.eventhandler.spring.annotation.EventContext
import global.genesis.eventhandler.spring.annotation.EventValidate
import global.genesis.eventhandler.spring.annotation.GenesisEventHandler

data class Create(val name: String = "", val qty: Int = 0)
data class Created(val id: String)
data class Validated(val normalisedName: String)

@GenesisEventHandler("CREATE")
class ValidatingEventHandler(
    private val events: EventProvider,
) {

    @EventValidate
    fun validate(details: Create): Validated {
        check(details.qty > 0) { "qty must be positive" }
        return Validated(details.name.uppercase())
    }

    @EventCommit
    fun commit(details: Create, @EventContext ctx: Validated): Created {
        // in-process only; throws if TOUCH isn't registered in this same process
        events.trigger("TOUCH", Update(details.name, details.qty))
        return Created(id = "${ctx.normalisedName}-${details.qty}")
    }
}
```

</TabItem>
<TabItem value="java">

```java
import global.genesis.eventhandler.spring.annotation.EventCommit;
import global.genesis.eventhandler.spring.annotation.EventContext;
import global.genesis.eventhandler.spring.annotation.EventValidate;
import global.genesis.eventhandler.spring.annotation.GenesisEventHandler;

@GenesisEventHandler("CREATE")
public class ValidatingEventHandler {

    private final EventProvider events;

    public ValidatingEventHandler(EventProvider events) {
        this.events = events;
    }

    @EventValidate
    public Validated validate(Create details) {
        if (details.getQty() <= 0) {
            throw new IllegalStateException("qty must be positive");
        }
        return new Validated(details.getName().toUpperCase());
    }

    @EventCommit
    public Created commit(Create details, @EventContext Validated ctx) {
        // in-process only; throws if TOUCH isn't registered in this same process
        events.trigger("TOUCH", new Update(details.getName(), details.getQty()));
        return new Created(ctx.getNormalisedName() + "-" + details.getQty());
    }
}
```

</TabItem>
</Tabs>

`@EventContext` is optional here, since the `commit` parameter type (`Validated`) already exactly matches what `@EventValidate` returns — the framework injects it either way. The constructor-injected `EventProvider` is unrelated to that context injection and works the same way on a validating handler as it does on a commit-only one.

## Configuration options

### Handler annotation(s)

- `@GenesisEventHandler("EVENT_NAME")` on a class marks it as a single-event handler. It may declare one `@EventValidate` method and must declare exactly one `@EventCommit` method.
- `@GenesisEventController("PREFIX")` on a class groups several related events together. Each method annotated `@EventMapping("SUFFIX")` becomes its own event, registered as `PREFIX_SUFFIX` (or just `SUFFIX` if the prefix is empty). A controller class must **not** declare `@EventValidate`/`@EventCommit` methods — there is no automatic validate/commit split per method inside a controller; a mapped method either handles the request outright or inspects `@IsValidateOnly` itself (see below).
- A class cannot carry both `@GenesisEventHandler` and `@GenesisEventController` — that combination is rejected at start-up, as is a controller with no matching methods, a single handler with no commit method, or more than one commit method.
- `EventHandlerType` (`STANDARD` / `INTERNAL` / `APPROVABLE` / `DEFAULT`, which resolves to `STANDARD`) is settable on the class or per-method, to influence routing and visibility. `STANDARD` is the default, UI-exposed case. `INTERNAL` is enforced at the router level: once an event is marked `INTERNAL`, the router will not expose it externally. `APPROVABLE` exists only as a value today — there's no supporting machinery for a multi-party approval flow, so setting it doesn't currently change a handler's behaviour (see [Limitations](#limitations)).

Parameter-level injection available on a validate/commit/mapping method:

| Annotation | Effect |
|---|---|
| *(none)* | The event payload, unless the parameter type is `Event<T>` (`global.genesis.message.core.event.Event`), in which case it's the full envelope instead. |
| `@UserName` | Injects the triggering user's username, as a `String`. |
| `@EventContext` | Injects the value returned by the paired `@EventValidate` method. Optional if the parameter type already matches. |
| `@IsValidateOnly` | Injects a `Boolean` reflecting whether the request is a `validate=true` pre-flight — see below for where this actually takes effect. |

A parameter typed as the full envelope has access to more than just the payload — for example, the triggering user's name, off `Event.userName`:

`@RequiresAnyRight`/`@RequiresAllRights` are checked against `RightSummaryCache` before the handler method runs; an unauthorised user gets a not-authorised nack and the method body never executes. They can sit on the class, on an individual `@EventMapping` method, or both (both checks then apply — logical AND). This path is genuinely wired and tested.

`@RequiresAuth(mapName, fields)` is also available, intended for row-level/dynamic authorisation against a Genesis authorization map, but it is **not enforced today** — it's parsed into a model attached to the handler definition and nothing consults it. Don't rely on it for row-level authorisation yet; use `@RequiresAnyRight`/`@RequiresAllRights` for anything that must actually be checked.

### Validation

`@EventValidate` runs on every incoming request for its event, including ones sent with `validate=true` (a pre-flight check), and its return value becomes the commit-phase context. When a request has `validate=true`, the framework itself never invokes `@EventCommit` — it returns whatever `@EventValidate` produced, converted to an ack or nack, without running the commit method. You don't need to check `event.validate` yourself — this is handled for both validating and commit-only handlers (a commit-only handler just acks empty instead of running validation logic first).

An exception thrown from `@EventValidate` on any request, not just `validate=true`, skips `@EventCommit` and is mapped to a nack the same way an exception from `@EventCommit` would be — see [Acknowledgement / rejection](#acknowledgement--rejection) below.

Bean Validation is partially wired: a parameter can be annotated `@jakarta.validation.Valid` or `@org.springframework.validation.annotation.Validated`, and the scanner records that on the parameter definition — but nothing downstream currently runs Bean Validation against it. Putting `@Valid` on a payload parameter today does not actually validate anything through this module; write your own checks in `@EventValidate` instead.

#### Manual validate/commit control

Occasionally one method needs to see both phases itself rather than have the framework split them — for example, to make a "dry run" flag explicit rather than implicit. `@IsValidateOnly` supports this, but **only on a `@GenesisEventController`/`@EventMapping` method**:

<Tabs defaultValue="kotlin" values={[{ label: 'Kotlin', value: 'kotlin', }, { label: 'Java', value: 'java', }]}>
<TabItem value="kotlin">

```kotlin
@GenesisEventController("ADMIN")
class AdminEventController {

    @EventMapping("PURGE")
    fun purge(details: Update, @IsValidateOnly validateOnly: Boolean): PurgeResult =
        PurgeResult(name = details.name, dryRun = validateOnly)
}
```

</TabItem>
<TabItem value="java">

```java
@GenesisEventController("ADMIN")
public class AdminEventController {

    @EventMapping("PURGE")
    public PurgeResult purge(Update details, @IsValidateOnly boolean validateOnly) {
        return new PurgeResult(details.getName(), validateOnly);
    }
}
```

</TabItem>
</Tabs>

On a single `@GenesisEventHandler`'s `@EventCommit` method, adding an `@IsValidateOnly` parameter compiles and injects a value, but has no effect on behaviour — the framework always auto-skips that method on a `validate=true` request before your code runs. If you need manual validate/commit control in one method, it has to be a controller method.

### Acknowledgement / rejection

A handler method's return value is converted to an `EventReply` automatically:

- Returning `EventReply.EventAck`/`EventReply.EventNack` directly is passed through unchanged.
- `null`, `Unit`, or a `void` method becomes an empty `EventAck`.
- Any other value becomes `EventAck(generated = listOf(thatValue))`, or `EventAck(generated = thatList)` if it's a `List<*>`.

For full manual control, inject an `EventProvider` (see below) and use its `ack(generated)`, `nack(errorCode, message)` and `warningNack(message)` helpers to build the reply by hand.

Exceptions are mapped to nacks through the following mechanisms:

- A per-handler `@EventExceptionHandler([SomeException::class])` method, which takes priority for exceptions thrown by that handler's own methods.
- A separate class annotated `@EventControllerAdvice`, with its own `@EventExceptionHandler` methods, registers globally and is consulted for any handler with no matching handler of its own. An advice class with no `@EventExceptionHandler` methods fails registration.
- A custom exception class annotated `@EventWarning(status = ...)` is treated as a business warning — the resulting `EventNack` carries it as a `warning` rather than an `error`.
- Any exception that doesn't match one of the above falls back to a default mapping: an `IllegalArgumentException` produces a nack carrying its message as the error, while any other exception (including the `IllegalStateException` thrown by `commit` above when `details.name` is neither `"warn"` nor `"custom"`) is treated as an internal error and produces a generic internal-error nack, with the exception's own message not exposed to the client.

An `@EventExceptionHandler` method must return `EventReply` and take exactly one `Throwable`-subtype parameter, checked at start-up:

<Tabs defaultValue="kotlin" values={[{ label: 'Kotlin', value: 'kotlin', }, { label: 'Java', value: 'java', }]}>
<TabItem value="kotlin">

```kotlin
import global.genesis.eventhandler.spring.annotation.EventCommit
import global.genesis.eventhandler.spring.annotation.EventExceptionHandler
import global.genesis.eventhandler.spring.annotation.GenesisEventHandler
import global.genesis.message.core.HttpStatusCode
import global.genesis.message.core.error.StandardError
import global.genesis.message.core.event.EventReply

@EventWarning(status = HttpStatusCode.Conflict)
class WarningException(message: String) : RuntimeException(message)

class CustomException(message: String) : RuntimeException(message)

@GenesisEventHandler("EXPLODE")
class ExplodingEventHandler {

    @EventCommit
    fun commit(details: Update) {
        when (details.name) {
            "warn" -> throw WarningException("already exists")
            "custom" -> throw CustomException("custom failure")
            else -> throw IllegalStateException("boom")
        }
    }

    // Handled locally: takes priority over any global advice for this handler's own exceptions.
    @EventExceptionHandler([CustomException::class])
    fun onCustom(ex: CustomException): EventReply =
        StandardError("CUSTOM", "handled locally: ${ex.message}", HttpStatusCode.BadRequest)
            .toEventNackError()
}
```

</TabItem>

```java
import global.genesis.eventhandler.spring.annotation.EventExceptionHandler;
import global.genesis.eventhandler.spring.annotation.GenesisEventHandler;
import global.genesis.message.core.HttpStatusCode;
import global.genesis.message.core.error.StandardError;
import global.genesis.message.core.event.EventReply;

    }

public class CustomException extends RuntimeException {
    public CustomException(String message) {

@GenesisEventHandler("EXPLODE")

    @EventCommit
    public void commit(Update details) {
        switch (details.getName()) {
            case "warn":
                throw new WarningException("already exists");
            case "custom":
                throw new CustomException("custom failure");
            default:
                throw new IllegalStateException("boom");
        }
    }

    // Handled locally: takes priority over any global advice for this handler's own exceptions.
    @EventExceptionHandler({CustomException.class})
    public EventReply onCustom(CustomException ex) {
        StandardError error = new StandardError(
                "CUSTOM", "handled locally: " + ex.getMessage(), HttpStatusCode.BadRequest);
        return new EventReply.EventNack(error); // vararg error constructor — unambiguous
    }
}
```

</TabItem>
</Tabs>

`EventReply.EventNack`'s primary constructor takes `warning` before `error` (`EventNack(warning: List<GenesisError> = ..., error: List<GenesisError> = ...)`), which is easy to get backwards positionally from Java — the vararg secondary constructor (`EventNack(vararg error: GenesisError)`) shown above maps unambiguously onto `error` instead.

`@ExposeClientError` also exists, documented as marking an exception's message safe to surface to the client instead of being masked — but it is not read anywhere in the current implementation. In practice, today, an exception's message reaches the client nack regardless of whether `@ExposeClientError` is present, so don't design a "mask by default, opt in to expose" flow around it yet.

### Triggering other events

A handler can call another event from within its own commit logic by injecting an `EventProvider` — a suspending variant (`global.genesis.eventhandler.spring.service.EventProvider`) for `suspend` call sites, and a blocking one (`global.genesis.eventhandler.spring.service.blocking.EventProvider`) for everything else, including Java:

<Tabs defaultValue="kotlin" values={[{ label: 'Kotlin (suspending)', value: 'kotlin', }, { label: 'Java (blocking)', value: 'java', }]}>
<TabItem value="kotlin">

```kotlin
import global.genesis.eventhandler.spring.annotation.EventCommit
import global.genesis.eventhandler.spring.annotation.GenesisEventHandler
import global.genesis.message.core.event.EventReply

@GenesisEventHandler("CREATE_AND_TOUCH")
class CreateAndTouchEventHandler(
    private val events: EventProvider,
) {
    @EventCommit
    suspend fun commit(details: Create): EventReply {
        // in-process only; throws if TOUCH isn't registered in this same process
        events.trigger("TOUCH", Update(details.name, details.qty))
        return events.ack()
    }
}
```

</TabItem>
<TabItem value="java">

```java
import global.genesis.eventhandler.spring.annotation.EventCommit;
import global.genesis.eventhandler.spring.annotation.GenesisEventHandler;
import global.genesis.message.core.event.EventReply;

@GenesisEventHandler("CREATE_AND_TOUCH")
public class CreateAndTouchEventHandler {

    private final EventProvider events;

    public CreateAndTouchEventHandler(EventProvider events) {
        this.events = events;
    }

    @EventCommit
    public EventReply commit(Create details) {
        Update touch = new Update(details.getName(), details.getQty());
        // in-process only; throws if TOUCH isn't registered in this same process
        events.trigger("TOUCH", touch);
        return events.ack();
    }
}
```

</TabItem>
</Tabs>

`trigger(eventName, payload)` is in-process only — it looks the target event up directly in the local registry, and throws if nothing is registered under that name in the *same* process; it does not fall back to a remote call. For a handler registered in a different process, use `triggerRemote(eventName, payload)` (suspends or blocks for the reply) or `triggerAsync(eventName, payload)` (fire-and-forget), both resolved via `ServiceDiscovery`.

### Suspend handlers — Kotlin only

Any `@EventValidate`/`@EventCommit`/`@EventMapping` method may be a Kotlin `suspend fun`; the scanner detects the compiler-injected `Continuation` parameter and the handler is registered as an asynchronous handler automatically, with no extra annotation needed:

```kotlin
import global.genesis.eventhandler.spring.annotation.EventCommit
import global.genesis.eventhandler.spring.annotation.GenesisEventHandler

@GenesisEventHandler("TOUCH_ASYNC")
class SuspendCommitOnlyEventHandler {

    @EventCommit
    suspend fun commit(details: Update) {
        // ... suspending work, e.g. a coroutine-based repository call
    }
}
```

There is no Java equivalent for this one. The scanner detects a suspend function purely from a JVM-level signal that only the Kotlin compiler produces — a trailing `kotlin.coroutines.Continuation` parameter — and a Java method can't reproduce that signature. If you need non-blocking handling from a Java class, look at making the surrounding call non-blocking some other way outside this module; there's no `@Async`-style alternative offered here.

## Limitations

This module is real, working code with test coverage for everything described above, but it is genuinely incomplete. Worth knowing before you plan around it:

- **There is no transaction control.** Earlier versions of the annotations carried a `transactional` flag; it has since been removed entirely, and there is no replacement. A handler method that needs a database transaction has to manage it itself — see [JPA data access: Transactions](../jpa-data-access#transactions) for how transaction boundaries and rollback work when a handler uses Spring Data JPA.
- **Approvable workflows are not supported.** `EventHandlerType.APPROVABLE` exists as a value, but the return types needed to drive a multi-party approval flow aren't consumed anywhere in the handler-invocation path. Don't build an approval-based feature on this module today — use GPAL's [pending approval workflow](/develop/server-capabilities/core-business-logic-event-handler#approval-workflow) instead.
- **`@RequiresAuth` (row-level/dynamic authorisation) is parsed but not enforced.** Only the static `@RequiresAnyRight`/`@RequiresAllRights` checks actually run.
- **`@IsValidateOnly` only takes effect on a `@GenesisEventController`/`@EventMapping` method**, not on a single `@GenesisEventHandler`'s `@EventCommit` method — see [Manual validate/commit control](#manual-validatecommit-control) above.
- **Bean Validation (`@Valid`/`@Validated`) on a payload parameter has no effect.** The annotation is recorded but nothing runs validation against it.
- **`@ExposeClientError` has no observable effect.** An exception's message reaches the client nack either way.
- **Java `record` classes crash bean creation** for a handler or payload type — always use a Kotlin `data class` or an ordinary Java class instead.

Two of these are easy to trip over in practice. Both reuse classes already defined earlier on this page.

## Testing

The dependency and plugin requirements in [Getting set up](#getting-set-up) apply to a test the same as to a full process. What differs is the rest: `@GenesisSpringTest` (see [Test tooling](../test-tooling)) supplies the five platform beans `GenesisSpringEventHandlerConfig` expects — `RightSummaryCache`, `TypedEventManager`, `MetaDataRegistry`, `ServiceRegistry`, `ServiceDiscovery` — along with everything else a normal Genesis process environment would otherwise provide, so a test doesn't need a real Genesis process running. What it does **not** supply is your own handler bean, covered below.

The recommended pattern is a real Spring context and a real message client, sending events through the full path — `EventClientSync` (or its async/Rx equivalents) → `TypedEventManager` → your handler bean — rather than mocking the framework. This exercises rights checks, the validate/commit split, and exception handling for real, and lets you assert both the reply shape (`EventAck`/`EventNack`) and any side effects (a counter, or a row via an injected repository).

See [Test tooling](../test-tooling) for the annotations and base classes (`@GenesisSpringTest`, `EventClientSync`, `@UserRight`, `@ResetTableAfterTest`) that support this.

`@GenesisSpringTest` composes `@SpringBootTest(classes = [GenesisTestApplication::class])`, and `GenesisTestApplication` itself carries only `@Configuration` and `@EnableAutoConfiguration` — no `@ComponentScan`. The test context therefore performs no component scanning at all: a hand-written `@GenesisEventHandler`, `@GenesisEventController` or `@EventControllerAdvice` class is never discovered by package position, wherever it lives. It has to be contributed to the context explicitly, for example by listing it alongside `GenesisTestApplication`:

```kotlin
@GenesisSpringTest
@SpringBootTest(classes = [GenesisTestApplication::class, ValidatingEventHandler::class])
class CreateEventHandlerTest {
    // ...
}
```

or via `@Import(ValidatingEventHandler::class)`, or a nested `@TestConfiguration` that declares it as a `@Bean`. This is different from a generated Spring Data repository such as [Test tooling: A simple example](../test-tooling#a-simple-example)'s `TradeRepository`, which arrives through autoconfiguration and needs no such step — don't generalise from that example to your own handler classes.

### A worked example

`EventClientSync.sendEvent(...)` returns an `EventReply` — the same sealed `EventReply.EventAck`/`EventReply.EventNack` type the handler itself returns (see [Acknowledgement / rejection](#acknowledgement--rejection)). Branch on it to assert the reply shape, and check any side effect (a counter, or a row via an injected repository) inside the ack branch. Reusing `Create`/`ValidatingEventHandler` from [above](#example-configuration):

<Tabs defaultValue="kotlin" values={[{ label: 'Kotlin', value: 'kotlin', }, { label: 'Java', value: 'java', }]}>
<TabItem value="kotlin">

```kotlin
import global.genesis.message.core.event.EventReply

@GenesisSpringTest
class CreateEventHandlerTest {

    @Autowired
    lateinit var client: EventClientSync

    @Test
    fun `acks and creates`() {
        when (val reply = client.sendEvent(details = Create(name = "widget", qty = 3), messageType = "CREATE")) {
            is EventReply.EventAck -> {
                // assert side effects here, e.g. a row via an injected repository
            }
            is EventReply.EventNack -> error("expected an ack, got a nack: ${reply.error}")
        }
    }

    @Test
    fun `nacks a non-positive quantity`() {
        when (val reply = client.sendEvent(details = Create(name = "widget", qty = 0), messageType = "CREATE")) {
            is EventReply.EventNack -> assert(reply.error.isNotEmpty())
            is EventReply.EventAck -> error("expected a nack, got an ack")
        }
    }

    @Test
    fun `also runs the triggered TOUCH handler`() {
        // CreateAndTouchEventHandler's commit calls events.trigger("TOUCH", ...) in-process;
        // trigger() throws if no TOUCH handler is registered in this process, so reaching an
        // ack here is what proves the triggered TOUCH handler actually ran.
        when (val reply = client.sendEvent(details = Create(name = "widget", qty = 3), messageType = "CREATE_AND_TOUCH")) {
            is EventReply.EventAck -> {
                // the TOUCH side effect ran
            }
            is EventReply.EventNack -> error("expected an ack, got a nack: ${reply.error}")
        }
    }
}
```

```java
import global.genesis.message.core.event.EventReply;

@GenesisSpringTest
class CreateEventHandlerTest {

    @Autowired
    private EventClientSync client;

    @Test

        assertFalse(((EventReply.EventNack) reply).getError().isEmpty());

                .withMessageType("CREATE_AND_TOUCH")

    }
```
