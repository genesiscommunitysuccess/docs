JUnit 5 support for Spring-based Genesis applications, parallel to [GenesisJunit](/develop/server-capabilities/testing-api).

## Overview

`genesis-spring-testsupport` is the JUnit 5 equivalent of GenesisJunit for a Spring Boot/JPA Genesis application. Its single entry point, `@GenesisSpringTest` (`global.genesis.springboot.test.GenesisSpringTest`), composes `@SpringBootTest` and boots the same underlying test-context machinery GenesisJunit uses — a live in-memory SQL database, message server, and Guice injector — wiring it into the Spring test context in place of the production bootstrap. Genesis's test clients (`EventClientSync`/`Async`/`Rx`/`Blocking`, `RequestClientSync`/`Async`/`Rx`/`Blocking`, `DataServerQueryViewClient`, `DataServerSubscriptionClientAsync`/`Rx`, `InMemoryTestAuthCache`) are exposed as Spring beans, so a test can `@Autowired` them directly; anything else — any platform singleton with no Spring binding of its own — is still reachable via `@Autowired lateinit var injector: Injector`.

`@GenesisSpringTest` only supports the SQL `DbLayer`, and is gated with `@EnabledIfSystemProperty(named = "DbLayer", matches = "SQL")`: without `-DDbLayer=SQL` set, tests are silently skipped rather than failed. Add a test dependency on `genesis-spring-testsupport` (an ordinary library module, not a test-fixtures jar) to pick up the annotation and its supporting infrastructure — no further wiring is required.

If you're testing a classic GPAL script app instead, use `GenesisJunit`/`GenesisSharedContextJunit` from `genesis-testsupport` directly. This module is the Spring-shaped equivalent, not a replacement.

## Annotations

`@GenesisSpringTest` honours the same class-level Genesis test annotations as GenesisJunit, all from `global.genesis.testsupport.jupiter`, walking the enclosing-class chain so a `@Nested` class inside an annotated outer class still picks up its configuration. Because every test method — and every test class whose Spring configuration matches — shares *one* Genesis runtime (see [Context caching](#context-caching)), most of these only work at class level; `@ResetTableAfterTest` is the one exception implemented at method level.

- **`@GenesisSpringTest`** — the single entry point described above. Class level only. Composes `@SpringBootTest(classes = [GenesisTestApplication::class])` together with `@Tag("DatabaseTest")` and the `DbLayer=SQL` gate.
- **[`@TestScriptFile`](/develop/server-capabilities/testing-api#testscriptfile)** — loads a GPAL script file for the test. Class level only under `@GenesisSpringTest`.
- **[`@CsvData`](/develop/server-capabilities/testing-api#csvdata)** — loads CSV fixture data. Supported at class level; a method-level `@CsvData` is rejected with an explicit error rather than silently ignored, since every method already shares the class's runtime.
- **[`@SysDefOverwrite`](/develop/server-capabilities/testing-api#sysdefoverwrite)** — overrides a system definition property for the test. Class level only.
- **[`@UserRight`](/develop/server-capabilities/testing-api#userright)** — grants a user rights for the test. Class level only.
- **[`@PackageScan`](/develop/server-capabilities/testing-api#packagescan)** — marks a class whose package should be scanned. Class level only.
- **[`@ResetTableAfterTest`](/develop/server-capabilities/testing-api#resettableaftertest)** — the one fixture annotation implemented at method level here: it snapshots the named tables before the class's tests run, then restores them after every test method. This reset isn't wrapped in a cache flush the way `GenesisSharedContextJunit`'s is, so a process with a data server or consolidator can retain view state derived from a table's pre-reset rows.

If you write your own annotation that composes `@GenesisSpringTest` (for example, to add a product-specific `@Tag`), keep `@Tag("DatabaseTest")` and the `DbLayer=SQL` gate travelling together — a class carrying only one of them runs in no CI job at all.

## Context caching

This is the main behavioural difference from GenesisJunit worth calling out. Spring's `TestContext` framework caches one Spring context — and so one Genesis runtime, one in-memory database — per distinct class-level Genesis configuration. Two `@GenesisSpringTest` classes with identical configuration share the same cached runtime; classes with different configuration each get their own. Every runtime in the same JVM addresses the same underlying database, so booting a new one truncates whatever a previous one had loaded — sharing is opt-out, not opt-in. The framework automatically reseeds a class's `@CsvData` fixtures if another cached context has truncated the shared database since that class last ran, but it's still worth choosing your sharing model deliberately:

- give a class `@DirtiesContext(classMode = DirtiesContext.ClassMode.AFTER_CLASS)` for a fresh runtime per class, or
- factor shared `@GenesisSpringTest` configuration into a common abstract base class so related test classes intentionally share one runtime, optionally bounding `spring.test.context.cache.maxSize` to cap how many live runtimes accumulate.

## A simple example

<Tabs defaultValue="kotlin" values={[{ label: 'Kotlin', value: 'kotlin', }, { label: 'Java', value: 'java', }]}>
<TabItem value="kotlin">

```kotlin
package global.genesis.springboot.jpa.test

import global.genesis.jpa.dao.Trade
import global.genesis.jpa.repo.TradeRepository
import global.genesis.springboot.test.GenesisSpringTest
import org.junit.jupiter.api.Test
import org.springframework.beans.factory.annotation.Autowired
import org.springframework.test.annotation.DirtiesContext
import java.time.LocalDate

@GenesisSpringTest
@DirtiesContext(classMode = DirtiesContext.ClassMode.AFTER_CLASS)
class BaseGenesisSpringTest {

    @Autowired
    lateinit var tradeRepository: TradeRepository

    @Test
    fun `test trade`() {
        val entry = Trade("A")
        entry.currencyId = "EUR"
        entry.price = 10.0
        entry.quantity = 1
        entry.tradeType = "NICE"
        entry.tradeDate = LocalDate.now()

        val saved = tradeRepository.save(entry)

        assert(entry.recordId != 0L)
        assert(saved.recordId == entry.recordId)
        assert(saved.pk == entry.pk)
    }
}
```

</TabItem>
<TabItem value="java">

```java
package global.genesis.springboot.jpa.test;

import global.genesis.jpa.dao.Trade;
import global.genesis.jpa.repo.TradeRepository;
import global.genesis.springboot.test.GenesisSpringTest;
import org.junit.jupiter.api.DisplayName;
import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.test.annotation.DirtiesContext;

import java.time.LocalDate;

import static org.junit.jupiter.api.Assertions.assertEquals;
import static org.junit.jupiter.api.Assertions.assertNotEquals;

@GenesisSpringTest
@DirtiesContext(classMode = DirtiesContext.ClassMode.AFTER_CLASS)
public class BaseGenesisSpringTestJava {

    @Autowired
    private TradeRepository tradeRepository;

    @Test
    @DisplayName("test trade")
    void testTrade() {
        Trade entry = new Trade("A");
        entry.setCurrencyId("EUR");
        entry.setPrice(10.0);
        entry.setQuantity(1);
        entry.setTradeType("NICE");
        entry.setTradeDate(LocalDate.now());

        Trade saved = tradeRepository.save(entry);

        assertNotEquals(0L, entry.getRecordId());
        assertEquals(entry.getRecordId(), saved.getRecordId());
        assertEquals(entry.getPk(), saved.getPk());
    }
}
```

</TabItem>
</Tabs>

`@GenesisSpringTest` is the only annotation needed to get a live Genesis runtime behind the Spring context. `TradeRepository` is a generated JPA repository, autowirable because its underlying `EntityManagerFactory`/repository beans come from the JPA auto-configuration running against the same in-memory database the test context set up. `@DirtiesContext(classMode = DirtiesContext.ClassMode.AFTER_CLASS)` is a choice to get a fresh Genesis runtime per test class rather than share Spring's context cache — see [Context caching](#context-caching) above for when to share instead.

Remember the prerequisite from the [overview](#overview): this class runs only when `-DDbLayer=SQL` is set — with no `DbLayer` set locally, `@EnabledIfSystemProperty` silently skips it rather than failing it.
