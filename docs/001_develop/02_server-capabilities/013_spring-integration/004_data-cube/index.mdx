Pivot, grouped, and flat queries over JPA entities, built for grid UIs such as [AG Grid's Server-Side Row Model](/develop/client-capabilities/grids/grid-pro), with no-probing security.

## Overview

A Genesis Spring/JPA application normally reads its data through hand-written repository queries
or the JPA entities generated from the dictionary (see [JPA data access](../jpa-data-access) and
[Data model foundation](../data-model)). The `genesis-data-cube-spring-boot-starter` module adds a
second, declarative layer on top of those same entities, purpose-built for grid UIs: flat, grouped
and pivoted queries, with paging, filtering and an HTTP wire protocol tuned for AG Grid's
Server-Side Row Model (SSRM).

Concretely, it gives you:

- A single query API, `Cube<ROW, FILTER>`, covering flat rows, DTO-projected rows, and
  aggregated/pivoted `Tuple` rows, all built from one consistent overload pattern (data →
  projection → window → scope).
- A factory, `CubeFactory`, that turns a JPA entity or a hand-written JPQL string into a cube, with
  the expensive state (query plan, pivot discovery, group counts) cached and shared across every
  caller of the same source.
- A declarative **exposure layer** (`CubeResource`, built via `CubeResourceBuilder` or the
  `cubeResource { }` Kotlin DSL) that turns a cube into a named HTTP resource: which operations
  exist, which columns callers may group/pivot/filter on, and what per-user row scoping applies.
- An internal HTTP wire layer exposing each resource at
  `/api/v1/cubes/{resource}/...`, with ETag caching and RFC 9457 `problem+json` errors.

Reach for it when you're building a grid-backed view — a positions blotter, a P&L breakdown, a
trade summary grouped and pivoted by currency — over data that already exists as a JPA entity,
without wanting to hand-write JPQL, pagination, filtering and caching for every such view. If the
view is a single named report shape, declare it as an **operation**; if the caller needs to choose
its own grouping/pivoting (an AG Grid SSRM datasource), expose the whole cube instead.

**What it is not:**

- Not a replacement for the classic Genesis Data Server / Request Server query path — it is a
  parallel, JPA/Hibernate-backed, HTTP-first surface that sits alongside it.
- Not a general-purpose reporting engine: filtering on an aggregated measure after grouping
  (`HAVING`) is not available over HTTP, and pivot discovery is capped (25 discovered columns by
  default; see [Query types](#query-types)).
- Not a write path. A cube is read-only; writes still go through the normal JPA repository/entity
  layer.

The cube engine queries JPA entities — it does not generate or map entities itself. Your entities
must already exist (from the dictionary-driven codegen described in
[Data model foundation](../data-model)) before you can build a cube over them, whether you use the
entity API directly or write JPQL against it.

## Set-up

Add the starter alongside [`genesis-spring-boot-starter`](../core):

```kotlin
dependencies {
    implementation("global.genesis:genesis-data-cube-spring-boot-starter")
}
```

Cube HTTP endpoints run through the same Spring Security filter chain as the rest of a Genesis
Spring application — see [Application core](../core) for how that chain is configured and how a
resource's `permission(...)` authority maps onto it.

Set these properties in the Spring module's `application.properties` (or `application.yml`) — see
[Getting started: Step 11](../getting-started#step-11-query-it):

| Property | Default | Purpose |
|---|---|---|
| `genesis.cube.pivot-ttl-millis` | `600000` (10 min) | Default time-to-live for a discovered pivot's column set, overridable per call |
| `genesis.cube.remembered-max-entries` | `1000` | Bound on how many distinct query plans/runners `CubeFactory` caches |
| `genesis.cube.web.max-page-size` | `1000` | Ceiling on the wire `size` parameter |
| `genesis.cube.web.max-filter-length` | `8192` | Character budget for the wire `filter` parameter before you should switch from GET to POST |
| `genesis.cube.web.max-sort-orders` | `64` | Ceiling on the number of comma-separated `sort` entries |
| `genesis.cube.pivot.max-columns` | `25` | Ceiling on the number of discovered pivot columns, and on an `OverflowPolicy.TopN` bound. Must be at least `1`; anything else fails startup |

The starter registers its HTTP layer through its own autoconfiguration, independently of
`GenesisSpringBootConfiguration` and `GenesisSpringWebConfig` — excluding those two from a test
context does not exclude a cube resource's endpoints.

The `curl`/wire examples below assume the default port `8080` — see [Getting started: Step
11](../getting-started#step-11-query-it) for how to run on a different port via plain Spring Boot
`server.port` configuration.

A `CubeResource` is an immutable descriptor, built via the Java-first `CubeResourceBuilder` or the
Kotlin `cubeResource { }` DSL, then published as a Spring bean. At startup, every `CubeResource`
bean is resolved and validated fail-fast: referenced columns must exist on the entity, a
JPQL-sourced exposure's projection aliases must all resolve to real columns on the source query, an
operation must declare at least one `groupBy`/aggregation, an operation's aggregates must suit
their columns' types (a `SUM` over a string column, for example), output column names must not
collide, and none may be named `ROW_REF` (reserved for row addressing). An operation may not be
named `query` or `schema`, since those paths belong to the dynamic-query and schema endpoints. A
`baseCriteria` template is validated here too (see
[Per-user row scoping](#per-user-row-scoping)). A misconfigured resource fails
application startup rather than the first request — a typo in a JPQL projection alias, for example,
throws at bean instantiation rather than silently mislabelling a column.

The smallest realistic exposure — one entity, one named operation, queried over HTTP — uses a
generated entity such as `Trade` (fields including `currencyId`, `tradeType`, `tradeDate`,
`quantity` and `price`):

<Tabs defaultValue="kotlin" values={[{ label: 'Kotlin', value: 'kotlin', }, { label: 'Java', value: 'java', }]}>
<TabItem value="kotlin">

```kotlin
@Configuration
class TradeCubeConfig {

    @Bean
    fun tradesByCurrency(): CubeResource = cubeResource<Trade> {
        // No exposeQuery(): only the named operation below is reachable over the wire.
        operation("byCurrency") {
            groupBy("currencyId")
            sum("quantity")
        }
        // FilterPolicy.GroupKeys (the default): callers may only filter on currencyId.
    }
}
```

</TabItem>
<TabItem value="java">

```java
@Configuration
public class TradeCubeConfig {

    @Bean
    public CubeResource tradesByCurrency() {
        return CubeResource.forEntity(Trade.class)
            .operation("byCurrency", op -> op
                .groupBy("currencyId")
                .sum("quantity"))
            .build();
    }
}
```

</TabItem>
</Tabs>

The bean name (`tradesByCurrency`) becomes the resource's wire name unless you pin one explicitly
with `.name("...")`. Query it at `/api/v1/cubes/{resource}/{operation}`, with `filter` as a
`criteriaMatch` expression (grammar covered in [Filtering](#filtering) below):

```
GET /api/v1/cubes/tradesByCurrency/byCurrency?filter=currencyId=='USD'&sort=quantity&page=0&size=50
```

`filter` here is gated to the operation's filterable columns — just `currencyId`, its own group
key. Filtering on `quantity` is rejected the same way a made-up column would be (see
[no-probing](#security)), because this operation declared no wider `FilterPolicy`. `sort`, `page`
and `size` default to unsorted, `0` and `100` respectively. A `POST` with a JSON body is equivalent
and preferred for longer filters.

A few further builder forms exist alongside the ones above: `exposeQuery()` with no customizer
exposes the dynamic query path with no restrictions (equivalent to an empty block); `sum`, `avg`,
`min` and `max` each take an optional second argument naming the output alias
(`sum("quantity", "totalQuantity")`), defaulting to the source column's own name; and `count()`
similarly takes an optional alias, as `count("widgetCount")`.

Like any endpoint behind a Genesis Spring Boot app's [session-token
authentication](../core#session-token-authentication), a cube endpoint needs a valid
`SESSION_AUTH_TOKEN` to answer anything but `401` — see [Testing an HTTP
endpoint](../test-tooling#testing-an-http-endpoint) for a complete `MockMvc` test against a
`@RestController` endpoint that stubs the session lookup instead of logging in for real; the same
shape works against a cube resource's endpoints.

The response is an envelope object: a `rows` array, `hasMore`, `rowKind`, an echoed `page`, and the
resolved `columns` — plus a `ROW_REF` per row when the operation's group key doubles as its
addressable identity. `ROW_REF` is an opaque, versioned identity string — round-trip it as
supplied rather than parsing or constructing one yourself.

## Query types

`Cube<ROW, FILTER>` answers three query shapes — flat, grouped, and pivoted — each following the
data → projection → window → scope order introduced above.

### Flat

Plain rows, no aggregation — `query(filter, pageable)`. A cube can be built over a mapped JPA
**entity** or over hand-written **JPQL** text; both share the same query surface once built. The
difference is only in how the source is declared and how the raw row is shaped (`ROW` is the entity
type for an entity cube, always `Tuple` for a JPQL cube, since it's a column projection):

<Tabs defaultValue="kotlin" values={[{ label: 'Kotlin', value: 'kotlin', }, { label: 'Java', value: 'java', }]}>
<TabItem value="kotlin">

```kotlin
@Autowired
lateinit var cubeFactory: CubeFactory

fun example(pageable: Pageable) {
    val trades: EntityCube<Trade> = cubeFactory.forEntity(Trade::class.java)
    val page = trades.query(filter = null, pageable = pageable) // CubeResult<Trade>
}
```

</TabItem>
<TabItem value="java">

```java
@Autowired
CubeFactory cubeFactory;

void example(Pageable pageable) {
    EntityCube<Trade> trades = cubeFactory.forEntity(Trade.class);
    CubeResult<Trade> page = trades.query(null, pageable);
}
```

</TabItem>
</Tabs>

`forJpql` parses and validates the query **eagerly**, at cube-creation time rather than on first
query — a bad source, or a join without `allowJoins = true` acknowledged explicitly (a join can
multiply rows and inflate `SUM`/`COUNT`), fails fast here rather than on a caller's request.

A read that selects rows by position (a page, or a limited list) comes back in a **total order** —
the caller's sort, then the row's own identity as a tiebreaker — so paging never repeats or drops
rows, provided the source has an identity to tiebreak on. An unpaged, unsorted read is explicitly
arbitrary order, not a stable one to rely on. See [Sorting](#sorting) for what a flat request can
sort on.

Every column in a flat query's response — including a computed one, such as a JPQL expression
column — carries `role: KEY` in the envelope's `columns` list, since none of them are aggregated;
`role` only distinguishes `KEY`/`MEASURE`/`ROW_REF` once a query groups or pivots (see
[Grouped](#grouped) below).

### Grouped

Group keys plus aggregates (`SUM`/`AVG`/`MIN`/`MAX`/`COUNT`), returned as `Tuple`s or a projection
DTO. A resource exposes this dynamically with `.exposeQuery { }`, bounding which columns a caller
may group by:

<Tabs defaultValue="kotlin" values={[{ label: 'Kotlin', value: 'kotlin', }, { label: 'Java', value: 'java', }]}>
<TabItem value="kotlin">

```kotlin
import global.genesis.spring.data.cube.resource.projection

val trades = cubeResource<Trade> {
    exposeQuery {
        projection<TradeFlat>()            // the caller's flat shape when it groups by nothing
        groupBy("currencyId", "tradeDate") // grouping is narrowed to these two columns
        pivotOn("currencyId")              // pivoting is narrowed to this one column
    }
}
```

</TabItem>
<TabItem value="java">

```java
CubeResource trades = CubeResource.forEntity(Trade.class)
    .exposeQuery(q -> q
        .projection(TradeFlat.class)
        .groupBy("currencyId", "tradeDate")
        .pivotOn("currencyId"))
    .build();
```

</TabItem>
</Tabs>

`TradeFlat` is a plain projection of `Trade`'s query-relevant columns:

<Tabs defaultValue="kotlin" values={[{ label: 'Kotlin', value: 'kotlin', }, { label: 'Java', value: 'java', }]}>
<TabItem value="kotlin">

```kotlin
data class TradeFlat(
    val tradeId: Long,
    val currencyId: String,
    val tradeDate: OffsetDateTime,
    val quantity: Int,
    val price: Double,
)
```

</TabItem>
<TabItem value="java">

```java
record TradeFlat(long tradeId, String currencyId, OffsetDateTime tradeDate, int quantity, double price) {}
```

</TabItem>
</Tabs>

Every shape goes through `POST /api/v1/cubes/{resource}/query` (there's no `GET` here — the query
shape doesn't fit comfortably in query parameters). A grouped request populates `groupKeys` and
`aggregates`:

```json
POST /api/v1/cubes/trades/query
{
  "groupKeys": [
    { "expr": { "type": "field", "attribute": "currencyId" } }
  ],
  "aggregates": [
    {
      "function": "SUM",
      "input": { "type": "field", "attribute": "quantity" },
      "alias": "totalQuantity"
    }
  ]
}
```

Every column named in the request must lie within the resource's visible set — the same
[no-probing rule](#security) that governs every other rejection. Post-aggregation filtering
(`HAVING`) is not available over HTTP.

The `POST .../query` body accepts only `filter`, `sort`, `page`, `size`, `groupKeys`, `aggregates`,
`calculations` and `pivot`, whichever query type you send. Any other field is rejected with `400`
rather than ignored — including `having` and `groupExpansion`, which exist on the in-process
`QueryRequest` but not on the wire.

See [Sorting](#sorting) for what a grouped request can sort on.

The same shape is also reachable directly in-process, with no resource involved — `Cube.query`
takes a `QueryRequest` overload alongside the flat one, always returning `Tuple`s:

<Tabs defaultValue="kotlin" values={[{ label: 'Kotlin', value: 'kotlin', }, { label: 'Java', value: 'java', }]}>
<TabItem value="kotlin">

```kotlin

fun example(pageable: Pageable) {
    val trades: EntityCube<Trade> = cubeFactory.forEntity(Trade::class.java)
    val grouped: CubeResult<Tuple> = trades.query(
        QueryRequest(
            groupKeys = listOf(GroupKey("currencyId", "currencyId")),
            aggregates = listOf(Aggregate(Function.SUM, "quantity", "totalQuantity")),
            filter = null,
        ),
        pageable,
    )
}
```

</TabItem>
<TabItem value="java">


### Pivoted

A grouped query whose `pivot` is set: one or more pivot dimensions are *discovered* — their
distinct values found by a live query against current data — and become dynamic output columns.
`noPivot()` on the same `exposeQuery` spec disables pivoting entirely for a resource that should
never allow it.

```json
POST /api/v1/cubes/trades/query
{
  "groupKeys": [
    { "expr": { "type": "field", "attribute": "tradeDate" } }
  ],
  "pivot": {
    "dimensions": [
      { "expr": { "type": "field", "attribute": "currencyId" } }
    ],
    "measures": [
      {
        "type": "aggregate",
        "aggregate": {
          "function": "SUM",
          "input": { "type": "field", "attribute": "quantity" }
        }
      }
    ]
  }
}
```

`currencyId` must additionally be in the resource's `pivotOn` allowlist to be used as a pivot
dimension. See [Sorting](#sorting) for which pivot columns a request can sort on.

The same request is callable directly in-process, exactly as for a grouped query:

<Tabs defaultValue="kotlin" values={[{ label: 'Kotlin', value: 'kotlin', }, { label: 'Java', value: 'java', }]}>
<TabItem value="kotlin">

```kotlin
@Autowired
lateinit var cubeFactory: CubeFactory

fun example(pageable: Pageable) {
    val trades: EntityCube<Trade> = cubeFactory.forEntity(Trade::class.java)
    val pivoted: CubeResult<Tuple> = trades.query(
        QueryRequest(
            groupKeys = listOf(GroupKey("tradeDate", "tradeDate")),
            pivot = PivotSpec(
                dimensions = listOf(PivotDimension("currencyId", PivotDiscovery.DISTINCT, false, null, null, false)),
                measures = listOf(PivotMeasure.OfAggregate(Aggregate(Function.SUM, "quantity", "totalQuantity"))),
            ),
            filter = null,
        ),
        pageable,
    )
}
```

</TabItem>
<TabItem value="java">

```java
@Autowired
CubeFactory cubeFactory;

void example(Pageable pageable) {
    EntityCube<Trade> trades = cubeFactory.forEntity(Trade.class);
    CubeResult<Tuple> pivoted = trades.query(
        new EntityQueryRequest<>(
            List.of(new GroupKey("tradeDate", "tradeDate")),
            List.of(),
            List.of(),
            new PivotSpec(
                List.of(new PivotDimension("currencyId", PivotDiscovery.DISTINCT, false, null, null, false)),
                List.of(new PivotMeasure.OfAggregate(new Aggregate(Function.SUM, "quantity", "totalQuantity")))),
            null,
            null,
            List.of()),
        pageable);
}
```

</TabItem>
</Tabs>

:::caution Pivot discovery is capped
Discovered pivot-column count is capped by `genesis.cube.pivot.max-columns` (default `25`; see
[Set-up](#set-up)). A pivot whose discovered set (or an `OverflowPolicy.TopN` bound) would exceed
the cap fails the request rather than silently truncating — use an `OverflowPolicy` (`TopN` or
`Within`) to keep a high-cardinality pivot dimension under it.
:::

A caller cannot request a group-expansion (an SSRM drill-down step) over HTTP: `groupExpansion` is
one of the fields the request body rejects (see [Grouped](#grouped)). Drill down with the next level
as the only group key and an equality filter on the parent path instead (see [Grid integration](#grid-integration)).

#### Explicit pivot values

Instead of discovering a dimension's values, a single-dimension pivot can name them explicitly.
Each value is typed (`int`, `long`, `decimal` or `string`; a decimal is sent as a string), and
`includeOther` adds a column that collects every row outside the listed values:

```json
"dimensions": [
  {
    "expr": { "type": "field", "attribute": "currencyId" },
    "values": [
      { "type": "string", "value": "USD" },
      { "type": "string", "value": "EUR" }
    ],
    "includeOther": true
  }
]
```

With explicit values the generated column names are known up front (`SUM_quantity_USD`,
`SUM_quantity_EUR`, `SUM_quantity_OTHER`), so the request can [sort](#sorting) on them. Explicit
`values` cannot be combined with an `overflow` policy or with `INTERVAL` discovery, and
`includeOther` is rejected without `values`.

### Sorting

Sorting applies to every query type above. `sort` has its own, smaller grammar: a comma-separated
list of column names, each optionally prefixed with `-` for descending — no prefix means ascending,
and the order between entries is significant for a multi-column sort. It compiles to a Spring Data `org.springframework.data.domain.Sort`,
and the number of comma-separated entries is capped by `genesis.cube.web.max-sort-orders` (see
[Set-up](#set-up)).

On `POST .../query`, a sort may only name the request's own output columns. A flat request can
sort on any visible column. A grouped request can sort on its group keys, aggregates and
calculations, using either the explicit alias or the derived name (`currencyId` for a group key,
`SUM_quantity` for an unaliased aggregate). A pivoted request can sort on generated columns only
when the pivot lists its [values explicitly](#explicit-pivot-values); discovered pivot columns can't
be sorted. Anything else is rejected with `400`, naming the columns that may be sorted.

On a `GET`, `sort`, `page` and `size` are query parameters. On any `POST` — `.../query` or a named
operation — they are fields of the JSON body alongside `filter`: `sort` as the same comma-separated
string, `page` and `size` as numbers. A `POST` that carries a query string at all is rejected with
`400`. Sorting the grouped request from [Grouped](#grouped) by total quantity, largest first, and
taking the first 50 groups:

```json
POST /api/v1/cubes/trades/query
{
  "groupKeys": [{ "expr": { "type": "field", "attribute": "currencyId" } }],
  "aggregates": [
    { "function": "SUM", "input": { "type": "field", "attribute": "quantity" }, "alias": "totalQuantity" }
  ],
  "sort": "-totalQuantity,currencyId",
  "page": 0,
  "size": 50
}
```

## Security

### No-probing and column visibility

The engine's central design invariant is that **a caller can never tell a hidden column from a
nonexistent one.** Every rejection — an unpermitted filter column, an unsortable one, a column
outside the visible set — surfaces as the same RFC 9457 `problem+json` error
(`.../problems/cube/query-rejected`), as HTTP 400 Bad Request with a standard `ProblemDetail` body.
The guarantee extends to the free-text `detail` field itself: its wording is a fixed template per
rejection *kind* (unpermitted filter column, unsortable column, outside the visible set) that only
ever echoes back column names the caller already supplied in their own request — so the string
never differs between a hidden column and a nonexistent one. Filtering `tradesByCurrency` on
`quantity` (a column that exists but isn't in this operation's `FilterPolicy` — see [Declaring a
cube resource](#declaring-a-cube-resource)) produces exactly the same shape a request naming a
made-up column would:

```json
{
  "type": "https://docs.genesis.global/problems/cube/query-rejected",
  "title": "Query rejected",
  "status": 400,
  "detail": "Filter references column(s) not filterable on cube resource 'tradesByCurrency': [quantity]. Only these columns may be filtered: [currencyId]"
}
```

Filtering on `bogusColumn` — a column that doesn't exist on `Trade` at all — produces the identical
shape, right down to the same `type`:

```json
{
  "type": "https://docs.genesis.global/problems/cube/query-rejected",
  "title": "Query rejected",
  "status": 400,
  "detail": "Filter references column(s) not filterable on cube resource 'tradesByCurrency': [bogusColumn]. Only these columns may be filtered: [currencyId]"
}
```

Splitting that error per reason would reintroduce, in a machine-readable field, exactly the
column-existence discrimination the rule exists to prevent.

That HTTP wrapping only happens at the HTTP endpoint boundary — an internal `@RestControllerAdvice`
scoped to that layer catches the rejection and renders it as the `problem+json` body above. Reached
in-process instead — via `CubeResourceRegistry.require(name)` returning a `ResolvedCubeResource`,
the same route the [per-user row scoping](#per-user-row-scoping) example uses — the identical
rejection surfaces as a raw, uncaught
`global.genesis.spring.data.cube.model.CubeRequestException`, carrying the same message as the
HTTP body's `detail`, just unwrapped. The no-probing guarantee lives specifically at the
`ResolvedCubeResource` layer: a raw `Cube`/`EntityCube`/`CubeFactory` has no `visibleColumns` or
`FilterPolicy` concept at all, so it enforces no column-visibility restriction of its own.

A `FilterPolicy` governs which columns a caller may reference in a **named operation's** filter,
beyond the columns it already groups by (implicitly filterable, since their values are already
enumerated in the output). It does not apply to the dynamic `.exposeQuery { }` path (see
[Complete usage examples](#complete-usage-examples)): that path is bounded purely by
`visibleColumns` — all source columns by default, or narrowed to exactly the fields named in an
explicit `projection<...>()` if the `exposeQuery` block declares one. Grouping and pivoting follow
the same default: if the `exposeQuery { }` block never calls `groupBy(...)`/`pivotOn(...)`, a caller
may group or pivot on any visible column — both stay open rather than defaulting to empty.

| Policy | Filterable columns |
|---|---|
| `GroupKeys` (default) | Group-by columns only |
| `GroupKeysAndAggregated` | Plus the columns the operation aggregates — chosen deliberately, since a measured column's per-row values become interval-recoverable through the filter bound even though the output never shows the column itself |
| `GroupKeysPlus(columns)` | Plus an explicit whitelist |
| `AllExcept(columns)` | Every column except a blacklist |
| `AnyColumn` | Every source column |

At most one policy may be declared per resource. A whitelist or blacklist is validated against the
entity's real columns at startup, so a typo fails application startup rather than silently letting
a column through (or blocking one you meant to allow).

### Per-user row scoping

A resource can declare `.baseCriteria("currencyId == :username")` — a `criteriaMatch` template
(v1 supports only the `:username` placeholder) that's ANDed server-side underneath every caller's
own filter, so two users querying the same resource only ever see their own rows. The reified
filter is itself part of the cache key, so per-user isolation of cached results falls out of
caching for free, and a caller cannot widen past their own scope by supplying a conflicting filter
value.

The template is checked at startup, so a mistake in it fails the application rather than the first
request. It must parse, reference only columns on the source, and be a single boolean expression
(a trailing `;` is enough to break it). On an entity-sourced resource, the template's own literals
must also convert to their column's type — an enum constant name that no longer exists, for
example. Values substituted for placeholders such as `:username` are not part of this check.

This mechanism is implemented and tested at the resource-resolution level, where you supply the
caller's identity yourself as a `PrincipalValues` binding:

<Tabs defaultValue="kotlin" values={[{ label: 'Kotlin', value: 'kotlin', }, { label: 'Java', value: 'java', }]}>
<TabItem value="kotlin">

```kotlin
@Bean
fun tradesByCurrencyScoped(): CubeResource = cubeResource<Trade> {
    baseCriteria("currencyId == :username") // reified per caller; scopes every request
    operation("byCurrency") {
        groupBy("currencyId")
        count()
    }
}

@Autowired
lateinit var registry: CubeResourceRegistry

fun tradesFor(username: String): CubeResult<*> {
    val trades = registry.require("tradesByCurrencyScoped")
    val principal = PrincipalValues { name -> if (name == "username") username else null }
    return trades.queryOperation("byCurrency", callerCriteria = null, PageRequest.of(0, 100), principal)
}
```

## Filtering

Filtering reuses the Genesis Data Server's own `criteriaMatch` grammar: a Groovy expression over
column names, parsed into a backend-neutral form and compiled independently by whichever backend
the cube uses (JPA `Criteria`, or JPQL text). The same grammar is used whether you call a cube
directly with a `criteriaMatch`-flavoured cube (`forEntityCriteria`/`forJpqlCriteria`) or supply a
resource's HTTP `filter` parameter/body field.

| Expression | Meaning |
|---|---|
| `currencyId == 'USD'` | equality |
| `currencyId == 'USD' \|\| currencyId == 'EUR'` | logical OR |
| `currencyId == 'USD' && price >= 5` | logical AND + comparison |
| `!(instrumentId == null)` | unary NOT + null check |
| `quantity % 2 == 0` | arithmetic (modulo) |
| `currencyId.toUpperCase() == 'USD'` | string method call |
| `currencyId.substring(0, 1) == 'U'` | substring |

The query endpoint accepts exactly four query parameters — `filter`, `sort`, `page` and `size` —
and nothing else. Any unknown or duplicate parameter is rejected with `400` rather than silently
ignored, which is deliberate: an unrecognised parameter would otherwise let a caller's own
cache-buster (for example `?_=<timestamp>`) silently defeat HTTP caching. On a `POST` the same
four travel in the JSON body instead, and any query string is rejected (see [Sorting](#sorting)).

A filter must be a single boolean expression. A malformed expression, an unknown column, an
unsupported method call, more than one statement (including a trailing `;`) or an expression that
isn't boolean is rejected, not thrown as a raw parser exception:

<Tabs defaultValue="kotlin" values={[{ label: 'Kotlin', value: 'kotlin', }, { label: 'Java', value: 'java', }]}>
<TabItem value="kotlin">

```kotlin

    filter = "currencyId == 'USD' && price >= 5",
    pageable = Pageable.ofSize(200),
)
```

</TabItem>

## Grid integration

The wire protocol and response shapes (the response envelope, row references) are generic JSON —
nothing in the HTTP layer imports or depends on AG Grid directly. The assumption that does exist is
architectural: the whole-cube `exposeQuery()` path's shape (group keys, aggregates, pivot
dimensions, flat vs. grouped vs. pivoted results) maps onto what an [AG Grid Server-Side Row
Model](/develop/client-capabilities/grids/grid-pro) datasource needs to drive `rowGroupCols`,
`groupKeys`, `pivotMode` and `filterModel`.

Translating AG Grid's `rowGroupCols`/`groupKeys`/`pivotMode`/`filterModel` into a cube query
request — including switching to a flat, equality-filtered query once a request reaches leaf rows,
for an SSRM drill-down step — is left to your own frontend adapter; the `/query` body shape itself
is exactly what's shown in [Query types](#query-types).

## Caching

Every `GET` response is validated with a three-part ETag covering: the request's identity (minted
from the effective, already-gated filter and shape — never the raw caller filter, since that could
leak a hidden base criterion), the source's freshness generation, and an era covering
discovered-pivot-column/memoized-count staleness.

- `GET` honours `If-None-Match` and answers `304 Not Modified`; `POST` never does, since a dynamic
  query has no cacheable identity to key on ahead of execution.
- A resource is only cacheable if the engine can prove its full source-table set and every source
  is trackable — an uncacheable cube simply always re-executes; nothing fails at startup because of
  it.

An initial request returns the ETag alongside the rows:

```
GET /api/v1/cubes/tradesByCurrency/byCurrency?filter=currencyId=='USD'

200 OK
ETag: "a1b2c3d4-42-7"
```

Replaying that value as `If-None-Match` on a later, identical request skips re-execution — and the
body — as long as none of the three parts (request identity, source freshness generation, pivot/count
era) have moved on:

```
GET /api/v1/cubes/tradesByCurrency/byCurrency?filter=currencyId=='USD'
If-None-Match: "a1b2c3d4-42-7"

304 Not Modified
```

`GET /api/v1/cubes/{resource}` describes a resource itself, before you issue any query against it —
whether rows are addressable, the identity columns, pagination/caching guarantees, and the
request-size limits:

```json
{
  "addressable": true,
  "identity": ["tradeId"],
  "paginationStable": true,
  "maxFilterLength": 8192,
  "maxPageSize": 1000,
  "defaultPageSize": 100,
  "maxSortOrders": 64,
  "maxPivotColumns": 25,
  "cacheable": true
}
```

This document is itself boot-time ETagged, and returns a `404` if the resource name is unknown *or*
if it exists but declares neither an operation nor `exposeQuery` — deliberately indistinguishable
from "unknown", extending the [no-probing rule](#security) to a resource's own existence.

`GET /api/v1/cubes/{resource}/schema` returns the same resource's wire shapes as JSON Schema, one
schema per shape:

- `envelope` — the response envelope wrapper
- `operationRequest` — a bare named-operation request
- `operations` — a map from operation name to the shape of that operation's result rows
- `queryRequest` — a `POST .../query` request body, including the limits the server enforces
  (page size, filter length, list sizes), so a request built from it won't be rejected on bounds
- `query` — the shape of a `POST .../query` result row. It is deliberately loose, because the
  columns depend on the request

`queryRequest` and `query` are `null` for a resource without `exposeQuery`.

Same ETag and `404` behaviour as the capability document above: cacheable, validated with
`If-None-Match`, answering `304 Not Modified` on a match, and `404` under the same condition — an
unknown resource, or one that declares neither an operation nor `exposeQuery`.

## Testing

[Testing an HTTP endpoint](../test-tooling#testing-an-http-endpoint) exercises a `@RestController`
without booting a real Genesis process: it excludes `GenesisSpringBootConfiguration` and
`GenesisSpringWebConfig`, then hand-declares a `TestApp` with a mocked `UserSessionCache`. A cube
resource can't use that recipe as-is — it needs a real JPA entity backed by a real database, which
only exists under `@GenesisSpringTest`, and `@GenesisSpringTest` never excludes those two
autoconfiguration classes.

`@GenesisSpringTest` composes `@SpringBootTest(classes = [GenesisTestApplication::class])` with no
`webEnvironment` override, so it defaults to Spring Boot's own `MOCK` — the same environment
`@AutoConfigureMockMvc` expects — and it leaves the starter's JPA autoconfiguration
(`GenesisDataConfig`) and cube autoconfiguration to wire up exactly as they would in a real process.
Combining the two annotations therefore gives you MockMvc in front of a fully booted cube resource,
querying a real JPA-backed data source, with no exclusion trick needed. As with [Testing an HTTP
endpoint](../test-tooling#testing-an-http-endpoint), stubbing the suspend `userLoggedInCheckDb`
cleanly needs mockito-kotlin's `onBlocking`, so this example is Kotlin-only:

```kotlin
package com.example.myapp.jpa

import global.genesis.session.UserSessionCache
import global.genesis.springboot.security.GenesisSessionAuthenticator.SESSION_AUTH_TOKEN_HEADER
import global.genesis.springboot.test.GenesisSpringTest
import org.joda.time.DateTime
import org.junit.jupiter.api.BeforeEach
import org.junit.jupiter.api.Test
import org.mockito.kotlin.doReturn
import org.mockito.kotlin.mock
import org.mockito.kotlin.stub
import org.springframework.beans.factory.annotation.Autowired
import org.springframework.boot.webmvc.test.autoconfigure.AutoConfigureMockMvc
import org.springframework.boot.test.context.SpringBootTest
import org.springframework.context.annotation.Bean
import org.springframework.context.annotation.Configuration
import org.springframework.context.annotation.Primary
import org.springframework.test.annotation.DirtiesContext
import org.springframework.test.web.servlet.MockMvc
import org.springframework.test.web.servlet.request.MockMvcRequestBuilders.get
import org.springframework.test.web.servlet.result.MockMvcResultMatchers.jsonPath
import org.springframework.test.web.servlet.result.MockMvcResultMatchers.status

@GenesisSpringTest
@SpringBootTest(classes = [GenesisTestApplication::class, TradeCubeConfig::class, CubeHttpQueryTest.SessionStub::class])
@AutoConfigureMockMvc
@DirtiesContext(classMode = DirtiesContext.ClassMode.AFTER_CLASS)
class CubeHttpQueryTest {

    @Autowired
    lateinit var mockMvc: MockMvc

    @Autowired
    lateinit var userSessionCache: UserSessionCache

    @BeforeEach
    fun stubValidSession() {
        userSessionCache.stub {
            onBlocking { userLoggedInCheckDb(VALID_TOKEN) } doReturn UserSessionCache.UserSessionRef(
                userName = "JaneDoe",
                sessionId = "session-1",
                token = VALID_TOKEN,
                expiryDateTime = DateTime.now().plusHours(1),
            )
        }
    }

    @Test
    fun `queries a real JPA-backed cube resource over its HTTP endpoint`() {
        mockMvc.perform(
            get("/api/v1/cubes/tradesByCurrency/byCurrency")
                .header(SESSION_AUTH_TOKEN_HEADER, VALID_TOKEN),
        )
            .andExpect(status().isOk)
            .andExpect(jsonPath("$.rowKind").value("GROUPED"))
            .andExpect(jsonPath("$.rows").isArray)
    }

    // A unique @Primary bean wins Spring's own resolution over the Guice-bridged
    // UserSessionCache (see Application core: BeanFactory bridging), without excluding
    // GenesisSpringBootConfiguration/GenesisSpringWebConfig — so the real cube/JPA
    // autoconfiguration stays wired.
    @Configuration(proxyBeanMethods = false)
    open class SessionStub {
        @Bean
        @Primary
        open fun userSessionCache(): UserSessionCache = mock()
    }

    private companion object {
        const val VALID_TOKEN = "valid-session-token"
    }
}
```

`TradeCubeConfig` is the `@Configuration` class declaring `tradesByCurrency` from [Declaring a cube
resource](#declaring-a-cube-resource) — like any hand-written bean under `@GenesisSpringTest`
(`GenesisTestApplication` does no component scanning), it has to be listed explicitly in
`@SpringBootTest(classes = [...])` alongside `GenesisTestApplication` and the session stub, or the
resource's bean — and its endpoint — is never registered. `userLoggedInCheckDb` is the method to
stub, not `userLoggedIn`: see [Testing an HTTP endpoint](../test-tooling#testing-an-http-endpoint)
for why. `@Primary` is what makes the override win: [Application core's BeanFactory
bridging](../core#beanfactory-bridging) notes that Spring's own resolution, including `@Primary`,
always takes priority over a Guice-bridged singleton like the real `UserSessionCache` this starter
would otherwise install.

Seed real rows through the same JPA repository a non-cube test would use — see [Test tooling: A
simple example](../test-tooling#a-simple-example) — and the response reflects them exactly as a
manual `curl` against a running app would; nothing about going through MockMvc changes the cube's
own query, filtering or no-probing behaviour described earlier on this page.

### Asserting that a bad declaration fails startup

An invalid cube resource fails application startup (see [Declaring a cube
resource](#declaring-a-cube-resource)). To assert that in a test, start a child context with
Spring Boot's `ApplicationContextRunner`, using the `@GenesisSpringTest` context as its parent.
The child imports the cube starter's own `CubeConfig` (`global.genesis.spring.data.cube.lifecycle`)
and declares the resource under test. The parent does not need to contain that resource: the
child's `CubeConfig` validates only the `CubeResource` beans declared in the child. See [Test
tooling](../test-tooling) for the test dependencies. In this example, `Widget` is a
generated entity with a `quality` field, and the bad declaration names an operation `query`, which
is reserved:

```java
                .projection(TradeFlat.class)
                .groupBy("currencyId", "tradeDate")
                .pivotOn("currencyId"))
            .build();
    }
}
```

</TabItem>
</Tabs>

A flat query, filtered but ungrouped:

```json
POST /api/v1/cubes/trades/query
{ "filter": "currencyId == 'USD'" }
```

The same resource, grouped by currency with a summed quantity:

```json
POST /api/v1/cubes/trades/query
{
  "groupKeys": [{ "expr": { "type": "field", "attribute": "currencyId" } }],
  "aggregates": [
    { "function": "SUM", "input": { "type": "field", "attribute": "quantity" }, "alias": "totalQuantity" }
  ]
}
```

And pivoted, with currency discovered as dynamic columns per trade date:

```json
POST /api/v1/cubes/trades/query
{
  "groupKeys": [{ "expr": { "type": "field", "attribute": "tradeDate" } }],
  "pivot": {
    "dimensions": [{ "expr": { "type": "field", "attribute": "currencyId" } }],
    "measures": [
      { "type": "aggregate", "aggregate": { "function": "SUM", "input": { "type": "field", "attribute": "quantity" } } }
    ]
  }
}
```

Before wiring up a frontend, `GET /api/v1/cubes/trades` tells you up front whether the resource is
addressable, cacheable, and what its page-size/filter-length limits are (see
[Caching](#caching)).

The dynamic `exposeQuery` path is reachable in-process too, without HTTP —
`ResolvedCubeResource.query`/`prepareQuery` are the `exposeQuery` counterparts of
[`queryOperation`/`prepareOperation`](#per-user-row-scoping): the request carries the query *shape*
only (its own `filter` must stay `null`), and the caller's `criteriaMatch` filter, if any, arrives as
a separate argument instead. Reproducing the grouped-by-currency query above:

<Tabs defaultValue="kotlin" values={[{ label: 'Kotlin', value: 'kotlin', }, { label: 'Java', value: 'java', }]}>
<TabItem value="kotlin">

```kotlin
@Autowired

fun example(pageable: Pageable) {
    val trades = registry.require("trades")
    val grouped: CubeResult<*> = trades.query(
        request = QueryRequest(
            groupKeys = listOf(GroupKey("currencyId", "currencyId")),
            aggregates = listOf(Aggregate(Function.SUM, "quantity", "totalQuantity")),
        ),
        callerCriteria = null,
        pageable = pageable,
    )
}
```

</TabItem>
<TabItem value="java">


### 2. A JPQL report with a column whitelist

A resource can be built from hand-written JPQL rather than a mapped entity — useful for a report
shape that doesn't map cleanly onto one entity's own columns — with an explicit `FilterPolicy`
widening beyond its group keys:

<Tabs defaultValue="kotlin" values={[{ label: 'Kotlin', value: 'kotlin', }, { label: 'Java', value: 'java', }]}>
<TabItem value="kotlin">

```kotlin
@Configuration
class TradeReportCubeConfig {

    private val tradeColumns =
        "select t.currencyId as ccy, t.price as px, t.quantity as qty, t.tradeType as tt from Trade t"

    @Bean
    fun tradeReport(): CubeResource = cubeResource(tradeColumns) {
        filterOn("tt") // whitelist beyond the group key
        operation("byCurrency") {
            groupBy("ccy")
            sum("qty")
        }
    }
}
```

</TabItem>
<TabItem value="java">

```java
@Configuration
public class TradeReportCubeConfig {

    private static final String TRADE_COLUMNS =
        "select t.currencyId as ccy, t.price as px, t.quantity as qty, t.tradeType as tt from Trade t";

    @Bean
    public CubeResource tradeReport() {
        return CubeResource.forJpql(TRADE_COLUMNS)
            .filterOn("tt")
            .operation("byCurrency", op -> op.groupBy("ccy").sum("qty"))
            .build();
    }
}
```

</TabItem>
</Tabs>

```
GET /api/v1/cubes/tradeReport/byCurrency?filter=ccy=='USD'&&tt=='BUY'
```

`ccy` (the group key) and `tt` (the whitelisted column) are both filterable; `px` is not, and a
request naming it is rejected with the same error as a nonexistent column, per the
[no-probing rule](#security).

### 3. A named operation alongside a dynamic `exposeQuery`

`exposeQuery { }` and `operation(...)` aren't mutually exclusive — a single resource can expose both
the dynamic query path and one or more named shortcuts over the same entity, each bounded
independently:

<Tabs defaultValue="kotlin" values={[{ label: 'Kotlin', value: 'kotlin', }, { label: 'Java', value: 'java', }]}>
<TabItem value="kotlin">

```kotlin
@Configuration
class TradesWithOperationCubeConfig {

    @Bean
    fun tradesWithOperation(): CubeResource = cubeResource<Trade> {
        exposeQuery {
            projection<TradeFlat>()
            groupBy("currencyId", "tradeDate")
        }
        operation("byCurrency") {
            groupBy("currencyId")
            sum("quantity")
        }
    }
}
```

</TabItem>
<TabItem value="java">

```java
@Configuration
public class TradesWithOperationCubeConfig {

    @Bean
    public CubeResource tradesWithOperation() {
        return CubeResource.forEntity(Trade.class)
            .exposeQuery(q -> q
                .projection(TradeFlat.class)
                .groupBy("currencyId", "tradeDate"))
            .operation("byCurrency", op -> op
                .groupBy("currencyId")
                .sum("quantity"))
            .build();
    }
}
```

</TabItem>
</Tabs>

`POST /api/v1/cubes/tradesWithOperation/query` reaches the dynamic path, bounded by `exposeQuery`'s
own `visibleColumns`/`groupBy`/`pivotOn`; `GET /api/v1/cubes/tradesWithOperation/byCurrency` reaches
the named shortcut, bounded by its own `FilterPolicy`. The two paths share the underlying cube and
cache, but each enforces its own column-visibility rules.

### 4. A typed projection on a JPQL-sourced `exposeQuery`

`.projection<...>()` isn't limited to an entity-backed resource — a JPQL source can use it too,
shaping the dynamic path's flat rows as a DTO instead of a raw `Tuple`:

<Tabs defaultValue="kotlin" values={[{ label: 'Kotlin', value: 'kotlin', }, { label: 'Java', value: 'java', }]}>
<TabItem value="kotlin">

```kotlin
@Configuration
class TradeReportDynamicCubeConfig {

    private val tradeColumns =
        "select t.currencyId as ccy, t.price as px, t.quantity as qty, t.tradeType as tt from Trade t"

    data class TradeReportRow(val ccy: String, val px: Double, val qty: Int, val tt: String)

    @Bean
    fun tradeReportDynamic(): CubeResource = cubeResource(tradeColumns) {
        exposeQuery {
            projection<TradeReportRow>()
            groupBy("ccy", "tt")
        }
    }
}
```

</TabItem>
<TabItem value="java">

```java
@Configuration
public class TradeReportDynamicCubeConfig {

    private static final String TRADE_COLUMNS =
        "select t.currencyId as ccy, t.price as px, t.quantity as qty, t.tradeType as tt from Trade t";

    record TradeReportRow(String ccy, double px, int qty, String tt) {}

    @Bean
    public CubeResource tradeReportDynamic() {
        return CubeResource.forJpql(TRADE_COLUMNS)
            .exposeQuery(q -> q
                .projection(TradeReportRow.class)
                .groupBy("ccy", "tt"))
            .build();
    }
}
```

</TabItem>
</Tabs>

A flat, ungrouped `POST /api/v1/cubes/tradeReportDynamic/query` returns rows shaped like
`TradeReportRow` — `ccy`, `px`, `qty` and `tt` — exactly as a JPQL-backed named operation would,
just without pinning the caller to one fixed group-by shape.
