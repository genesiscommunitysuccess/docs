By default, Genesis processes exchange messages with each other over raw TCP, and only GENESIS_ROUTER answers HTTP requests. If you switch a process to the WebSocket messaging channel, it keeps serving Genesis messaging and also answers plain HTTP on the same port: each of its request servers, event handlers and custom endpoints gets an HTTP route. You can call those routes directly from inside your cluster, or let the Genesis Router forward HTTP requests to them as a proxy.

A process stays on TCP, and loads none of the HTTP layer, until you configure the channel.

:::warning

Native HTTP on the process port has three known limitations. Until they are resolved, don't expose a process on the WebSocket channel to callers you don't trust.

- **Request servers and event handlers run as the caller-supplied `USER_NAME` header.** The session token is checked, but the user it belongs to isn't passed to the request server or event handler. They see whatever `USER_NAME` header the caller sends, so any logged-in caller can act as another user. With no header, the request runs as `UNKNOWN`, and a request server that declares permission codes rejects it. Custom endpoints are not affected; they receive the session user.
- **The session idle timeout isn't applied.** A token is accepted for as long as its session exists: until logout, or until the session is removed once the refresh-token lifetime has passed. `sessionTimeoutMins` isn't checked here, unlike requests that the router handles itself.
- **Requests proxied by the router skip some router checks.** See [HTTP proxy](/develop/server-capabilities/runtime-configuration/genesis-router/#http-proxy) on the Genesis Router page.

:::

## Enable the WebSocket channel

Set `messaging.channel` to `WEBSOCKET` in the network configuration YAML. Use `network-config.yaml` to change every process, or `network-config-<PROCESS_NAME>.yaml` to change one process. When both files exist, the process file is applied over the application file.

```yaml
messaging:
  channel: WEBSOCKET
```

Processes on TCP and processes on WebSocket can run side by side in the same application: a client picks the channel for each target process from what that process published to service discovery.

For the other `messaging` settings, including the `webSocket` and `http` blocks, see the [network configuration YAML reference](/develop/server-capabilities/runtime-configuration/service-encryption/network-configuration-yaml/#messaging-section).

## Routes

| Resource | Route | Example |
|---|---|---|
| Request server `HELLO_WORLD` | `GET /req-hello-world` | `GET /req-hello-world?REQUEST.NAME=World` |
| Event handler `EVENT_CUSTOM_MODIFY` | `POST /event-custom-modify` | body `{"DETAILS": {"NAME": "http-test"}}` |
| Data server | none | Data servers are served by the Genesis Router only |
| Custom endpoint | the method and path it declares | see [Custom endpoints on a process](#custom-endpoints-on-a-process) |

The route for a request server or event handler is its resource name converted from `UPPER_UNDERSCORE` to `lower-hyphen`, and request servers get a `req-` prefix. This is the same URL scheme the Genesis Router uses, so a URL that works through the router also works on the process port. Paths are matched exactly: `/EVENT_CUSTOM_MODIFY` returns 404.

Request and response bodies use the same JSON format as the router. The reply is the JSON form of the reply message; for example, an event handler replies with `"MESSAGE_TYPE": "EVENT_ACK"`.

## Status codes

| Situation | Status |
|---|---|
| No route for the path | 404 |
| The route exists, but not for this method | 405; the body lists the methods it accepts |
| No custom endpoint's request criteria accept the request, or more than one does | 406 |
| No session token, or an unknown one | 401 |
| Logged in, but without the endpoint's permission codes | 403 |
| Request body too large | 413 |
| The endpoint threw an exception | 500 |
| A reply from a request server or event handler, including a NACK | 200 |

A NACK from a request server or event handler comes back with status 200. The router's `strictHttpStatusCode` setting doesn't apply to the process port.

## Authentication

The process reads the session token from the `SESSION_AUTH_TOKEN` request header, and looks the session up in its own `USER_SESSION` table. Request server and event handler routes require a logged-in user, and don't check any permission codes at the route; permissioning inside the request server or event handler still applies. Custom endpoints apply the permissioning they declare.

To turn authentication off for a process's native HTTP, set the system definition item `HttpAuthDisabled` to `true` for that process. Every request is then treated as anonymous. The default is `false`.

## Custom endpoints on a process

A process on the WebSocket channel can load `*-web-handler.kts` files itself, instead of leaving them to GENESIS_ROUTER. Add the script file name to the process's `script` entry in `processes.xml`, comma-separated from any other scripts. The script content is the same as for the router. Each endpoint is registered on the process port and published to service discovery, so a router in proxy mode can forward requests to it.

```xml
<process name="POSITION_APP_EVENT_HANDLER">
  ...
  <script>position_app-eventhandler.kts,position_app-web-handler.kts</script>
  ...
</process>
```

Multipart uploads and file downloads work on the process port in the same way as on the router. For the script syntax, see [Custom endpoints](/develop/server-capabilities/integrations/custom-endpoints/).

## Internal resources

You can mark an event handler, request server or custom endpoint as `internal`. The process still serves it on its own port, so calls from inside your cluster work as before, but the Genesis Router refuses it to external callers with a 404. For custom endpoints, this only takes effect when the endpoint is loaded by a process and the router reaches it through the proxy. An endpoint that the router serves itself ignores `internal`.

A file-level setting applies to the definitions that come after it in the file, and you can override it on each definition.

```kotlin
// *-eventhandler.kts
eventHandler {
    internal = true                // every event handler defined after this line
    eventHandler<Trade>(name = "TRADE_SYNC") {
        internal = true            // or on one event handler
        // ...
    }
}

// *-reqrep.kts
requestReplies {
    config { internal = true }     // every request server in the file
    requestReply(TRADE) {
        config { internal = true } // or on one request server
    }
}

// *-web-handler.kts
webHandlers {
    internal = true                // every endpoint defined after this line
    endpoint(GET, "health") {
        internal = true            // or on one endpoint
        // ...
    }
}
```

## Through the Genesis Router

To route HTTP from the front end to these processes, enable the router's HTTP proxy. With the proxy on, the router forwards requests for resources owned by a process on the WebSocket channel, and streams the request and response through without buffering them. Requests for data servers, and for resources on TCP processes, are handled by the router as before.

See [HTTP proxy](/develop/server-capabilities/runtime-configuration/genesis-router/#http-proxy) on the Genesis Router page.
