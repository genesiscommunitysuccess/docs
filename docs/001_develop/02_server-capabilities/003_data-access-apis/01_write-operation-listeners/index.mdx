A write operation listener is your own code that the database layer calls after each successful write, inside the same transaction as that write. Any writes the listener makes through the transaction object it receives commit or roll back together with the write that triggered it.

Use a listener when an extra write must be atomic with every write, for example to maintain a derived table. Don't use one just to react to changes: a listener runs on every write in the process, so anything slow in it slows down every write. To react to changes, [subscribe](/develop/server-capabilities/data-access-apis/#subscribe-operations) to the data instead.

## The three listener interfaces

There is one listener interface for each style of API, all in the `global.genesis.db.bustxn` package. Each has a default no-op implementation. To replace it, provide your own implementation as a [`@Module`](/develop/server-capabilities/custom-components/#module).

A listener is only bound if its package is registered as a core extension package, which is scanned at start-up together with the platform's database layer. To register it, add an empty classpath resource file named after the listener's package, under `META-INF/global/genesis/bootstrap/extensions/`. For a listener in the package `com.example.listeners`, in your app module:

```text
src/main/resources/META-INF/global/genesis/bootstrap/extensions/com.example.listeners
```

Listing the package in a process's `<package>` section in processes.xml does not bind a listener.

The file must end up in the deployed app jar, on the classpath of every process that writes and should notify the listener. There is no property or flag that enables listener support.

A listener is bound in every process whose `<classpath>` includes the jar holding its extensions file, so a listener in a jar that every process loads is bound in all of them. A write listener runs inside the transaction of the process that makes the write, so it is always in-process: it sees only the writes made by the process it is bound in. To react to writes made by another process, [subscribe](/develop/server-capabilities/data-access-apis/#subscribe-operations) to the update queue instead, which is asynchronous and crosses process boundaries. To give different processes different listeners, put each listener, with its extensions file, in a module or jar that only that process's `<classpath>` includes. See [Processes](/develop/server-capabilities/runtime-configuration/processes/) for the `<classpath>` element.

When a process starts, it logs one of two lines from `RxDb`. `Database WriteOperationListener support not enabled` means no custom `WriteOperationListener` was bound in that process. `Enabling database WriteOperationListener support` means one was bound. Both lines are about `WriteOperationListener` only: they say nothing about `SyncWriteOperationListener` or `AsyncWriteOperationListener`, and the "not enabled" line is logged whether or not you have bound one of those. Check those two by their effect, for example by a side effect or log line in the listener itself after a write. A process whose only listener is a `WriteOperationListener` also logs `INFO ... No SyncWriteOperationListener bound; bridging WriteOperationListener onto the sync write path`. This is expected: the `WriteOperationListener` is being used for sync writes. If you expected a `WriteOperationListener` and see the "not enabled" line, check that the extensions file exists, is named exactly after the listener's package, and is in the process's classpath.

| Interface | Signature | `tx` |
|---|---|---|
| `AsyncWriteOperationListener` | `suspend fun onWriteResult(tx: AsyncDb, writeResults: List<WriteResult>)` | an [`AsyncDb`](/develop/server-capabilities/data-access-apis/#syncdb-and-asyncdb) bound to the write's transaction |
| `SyncWriteOperationListener` | `fun onWriteResult(tx: SyncDb, writeResults: List<WriteResult>)` | a [`SyncDb`](/develop/server-capabilities/data-access-apis/#syncdb-and-asyncdb) bound to the write's transaction |
| `WriteOperationListener` | `fun onWriteResult(tx: RxRecordWriteSupport<*, *, *>, writeResults: List<WriteResult>)` | an RxJava record API bound to the write's transaction |

Each [`WriteResult`](/develop/server-capabilities/data-access-apis/#write-result) holds the records the write saved and removed. To tell which operation a `WriteResult` describes, look at which of its two lists is empty, as the database does itself:

- `savedRecords` is empty: a delete. The deleted records are in `removedRecords`.
- `removedRecords` is empty: an insert. The new records are in `savedRecords`.
- Both have records: a modify. The two lists are the same size and are paired by position, so `removedRecords[i]` is the previous version of `savedRecords[i]`.

This listener keeps a `TRADE_SUMMARY` row in step with every `TRADE` that is saved:

```kotlin
import global.genesis.commons.annotation.Module
import global.genesis.db.DbRecord
import global.genesis.db.ModifyDetails
import global.genesis.db.SyncDb
import global.genesis.db.bustxn.SyncWriteOperationListener
import global.genesis.db.engine.WriteResult

@Module
class TradeSummaryListener : SyncWriteOperationListener {
    override fun onWriteResult(tx: SyncDb, writeResults: List<WriteResult>) {
        writeResults
            .flatMap { it.savedRecords }
            .filter { it.tableName == "TRADE" }
            .forEach { trade ->
                val summary = DbRecord("TRADE_SUMMARY").apply {
                    setString("TRADE_ID", trade.getString("TRADE_ID"))
                    setString("TRADE_STATUS", trade.getString("TRADE_STATUS"))
                }
                tx.upsert(ModifyDetails(summary, "TRADE_SUMMARY_BY_TRADE_ID"))
            }
    }
}
```

The table, index and field names in this example are placeholders for your own data model.

For what `ModifyDetails` is, see [Modify details](/develop/server-capabilities/data-access-apis/#modify-details).

Index names come from your data model. By default, the platform names an index `<TABLE_NAME>_BY_<FIELD_1>(_<FIELD_N>)`, as described in [primaryKey](/develop/server-capabilities/data-model/#primarykey), so a `TRADE_SUMMARY` table keyed on `TRADE_ID` gets `TRADE_SUMMARY_BY_TRADE_ID`. You can override the name with `.name()`.

A `WriteOperationListener` receives an `RxRecordWriteSupport` as `tx`. It offers the write methods only, bound to the write's transaction. They are `insert`, `modify`, `upsert`, `delete`, `recover` and their `All` variants, and each returns an RxJava `Single`. Block on each call on the thread that called you, as [described below](#writeoperationlistener-on-the-sql-write-path). Do not cast it to `RxDb`: anything done through `RxDb` runs outside the write's transaction. This listener records a `TRADE_EVENT` row for every `TRADE` that is saved:

```kotlin
import global.genesis.commons.annotation.Module
import global.genesis.db.DbRecord
import global.genesis.db.bustxn.WriteOperationListener
import global.genesis.db.engine.WriteResult
import global.genesis.db.rx.engine.RxRecordWriteSupport

@Module
class TradeEventListener : WriteOperationListener {
    override fun onWriteResult(tx: RxRecordWriteSupport<*, *, *>, writeResults: List<WriteResult>) {
        writeResults
            .flatMap { it.savedRecords }
            .filter { it.tableName == "TRADE" }
            .forEach { trade ->
                val event = DbRecord("TRADE_EVENT").apply {
                    setString("TRADE_ID", trade.getString("TRADE_ID"))
                    setString("TRADE_STATUS", trade.getString("TRADE_STATUS"))
                }
                tx.insert(event).blockingGet()
            }
    }
}
```

The table and field names in this example are placeholders for your own data model.

## Which listener is called

Bind only one write listener in each process: one of `WriteOperationListener`, `SyncWriteOperationListener` or `AsyncWriteOperationListener`. If you bind more than one, the behaviour is undefined. To run several pieces of logic in one process, write one listener that dispatches to your own classes. Writes from [GPAL Event Handlers](/develop/server-capabilities/core-business-logic-event-handler/) reach your listener like any other write. Each of the three receives a different `tx`: an `AsyncWriteOperationListener` gets an `AsyncDb`, a `SyncWriteOperationListener` gets a `SyncDb`, and a `WriteOperationListener` gets an `RxRecordWriteSupport`.

Which writes notify your listener also depends on its type. An `AsyncWriteOperationListener` is notified only by async (suspend) writes: `AsyncDb` and `AsyncEntityDb` suspend writes, and single `RxEntityDb` writes. It is not notified by `SyncDb` or `SyncEntityDb` writes, or by blocking views such as `AsyncEntityDb.sync()`. If a process also writes through `SyncDb`, `SyncEntityDb` or a `.sync()` view, an `AsyncWriteOperationListener` does not see those writes.

To switch to a different listener type, replace the old listener with the new one: move the old listener's logic into the new one and delete the old listener class. If the new listener is in a different package, register that package with its own extensions file (see *The three listener interfaces*), and delete the old package's file if nothing else in that package needs binding.

## How a listener is called

- The listener is called after the write, inside the write's transaction, and before the write is published to the update queue.
- It is called once per write call. A batch write such as `upsertAll` or `modifyAll` calls it once, with one `WriteResult` per record. An audited write is two writes (the record and its audit record), so it calls the listener twice.
- `tx` is bound to the same transaction. Writes you make through it commit or roll back with the triggering write, are published to the update queue after it, and don't call the listener again.
- If the listener throws an exception, or one of its own writes fails, the triggering write rolls back and nothing is published.
- Only an exception thrown before `onWriteResult` returns rolls the triggering write back. Work you hand to another thread is outside the transaction.
- Stay on the thread that called you (for `AsyncWriteOperationListener`, the coroutine). Handing work on `tx` to another thread or dispatcher breaks the transaction or deadlocks it. For `SyncWriteOperationListener` and `AsyncWriteOperationListener` nothing checks this. Unlike `WriteOperationListener`, which throws an error that explains the problem (see [below](#writeoperationlistener-on-the-sql-write-path)), a thread switch in these two shows up as a hang or a failed transaction, with no message that names the cause.

### `WriteOperationListener` on the SQL write path

When a `WriteOperationListener` is called for a write that didn't go through `RxDb`, its `tx` is backed by the write's own transaction. Block on every call you make through it, for example with `blockingGet()`, on the thread that called `onWriteResult`. A call through `tx` from any other thread fails with an error that explains this.

This requirement is new in 10.0. In 8.x, the write waited for `onWriteResult` to return, but reactive work the listener started on `tx` without blocking was neither enforced nor awaited. Because 8.x committed as soon as `onWriteResult` returned, that work raced the commit: it could be written in the same transaction, written after it, or fail without an error reaching the caller. If your 8.x listener did this, check the records it wrote. In 8.x, a `WriteOperationListener` was already called for `AsyncEntityDb` and `SyncEntityDb` writes as well, so which writes your listener sees has not changed; only the blocking requirement on `tx` is new.

Whether you need to change your listener depends on how it uses `tx`:

- A listener that already blocks on every `tx` call (for example with `blockingGet()`), or that calls `tx` only on the thread running `onWriteResult` with no `subscribeOn` or `observeOn`, needs no change.
- A listener that uses `tx` from another thread, or after `onWriteResult` returns, now gets an `IllegalStateException` on that thread. If `onWriteResult` waits for that work (for example with `blockingGet()`), the exception reaches it and the triggering write rolls back; if it doesn't wait, the triggering write and anything the listener wrote before the switch stay committed. If you have 8.x listener code that calls `subscribe()` on a `tx` call without blocking, change it to block.
