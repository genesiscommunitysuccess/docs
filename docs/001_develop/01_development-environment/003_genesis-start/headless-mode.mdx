In headless mode, Genesis Start runs without opening a window, and you drive it with its REST API. Everything you would normally do by clicking (bootstrapping, starting and stopping processes, running scripts, checking status, switching process profiles) is done with HTTP requests instead.

Use headless mode on build machines, in CI, or in a remote development environment with no display. It uses the same engine as the [desktop window](/develop/development-environment/genesis-start/), so the processes, profiles and behaviour described there all apply here too.

## What to expect

- **You need the REST API.** If it isn't enabled, Genesis Start logs an error and exits immediately with exit code 1:

  ```
  Headless mode requires REST to be enabled (remove --no-rest); exiting.
  ```

- **Nothing starts automatically.** Headless mode doesn't bootstrap or start any processes on its own. Once it's running, call `POST /api/bootstrap` or `POST /api/processes/application/start-all`, and check the operation it returns (see [Long-running operations](#long-running-operations)). You can't combine headless mode with `autoLaunch`: if you pass both, Genesis Start refuses to start.
- **The process list is ready straight away.** Genesis Start loads the project overview before the REST API starts listening, so your first request never sees an empty process list.
- On macOS, headless mode doesn't show an icon in the Dock.

If your project doesn't have Genesis Start yet, [enable it](/develop/development-environment/genesis-start/configuration/#enabling-genesis-start) first. The `google()` repository settings described there are needed for headless mode too, unless you use the standalone plugin.

## Starting headless mode

There are three ways to start headless mode. For most uses, the start script is best.

### The start script

The `writeStartScript` task writes a script that runs exactly the same command as `genesisStart` (the same Java, classpath, JVM arguments and flags), but without going through Gradle. You generate it once, then run it whenever you need to. (With the standalone plugin, the task is called `writeStartScript-standalone`.)

From your project's `server` directory, generate the script with the headless settings built in:

<Tabs defaultValue="windows" values={[{ label: 'Windows', value: 'windows', }, { label: 'Mac OSX / Linux', value: 'mac', }]}>
<TabItem value="windows">
```shell
.\gradlew.bat writeStartScript -Pgenesis.start.headless=true -Pgenesis.start.restEnabled=true -Pgenesis.start.restPort=18080
```
</TabItem>
<TabItem value="mac">
```bash
./gradlew writeStartScript -Pgenesis.start.headless=true -Pgenesis.start.restEnabled=true -Pgenesis.start.restPort=18080
```
</TabItem>
</Tabs>

This writes `start.sh` (or `start.bat` on Windows) to `build/genesis-start/`. That is the same folder where the classpath jar is, and where Genesis Start writes `output.log` and `error.log`.

Then run the script. It runs Genesis Start in the foreground, so on Mac or Linux, add `&` to get your shell back:

<Tabs defaultValue="windows" values={[{ label: 'Windows', value: 'windows', }, { label: 'Mac OSX / Linux', value: 'mac', }]}>
<TabItem value="windows">
```shell
build\genesis-start\start.bat
```
</TabItem>
<TabItem value="mac">
```bash
build/genesis-start/start.sh &
```
</TabItem>
</Tabs>

Any arguments you give the script are passed on to Genesis Start, after the ones built into it. This is how you pass the flags that have no Gradle property, such as a one-off [system definition override](/develop/development-environment/genesis-start/configuration/#overriding-a-property-for-a-single-run):

```bash
build/genesis-start/start.sh --system-definition-property DbHost=jdbc:postgresql://localhost:5433/genesis &
```

Things to know about the start script:

- It doesn't run as part of `genesisStart`; you run `writeStartScript` yourself. Running it also rebuilds the classpath jar the script uses.
- It only writes the script for the operating system Gradle is running on.
- The settings are fixed when the script is written. If you change one (for example, a different `restPort`), run `writeStartScript` again.
- `autoLaunch` is never built into the script, even if you set it. To use it with the desktop window, pass `--auto-launch` to the script when you run it.
- The script sets the database host, username and password as environment variables before it starts Genesis Start, so they don't appear on the command line. But the script file itself contains the password **in plain text**. The task tries to make the file readable only by you, but don't commit or share it. On Windows, `start.bat` uses `setlocal`, so those variables don't stay set in your command prompt afterwards.
- The script only changes how you start Genesis Start. You [stop it](#stopping-it) in the same way as before.

### With Gradle

For a one-off run, you can start headless mode with the Gradle task directly, from your project's `server` directory:

<Tabs defaultValue="windows" values={[{ label: 'Windows', value: 'windows', }, { label: 'Mac OSX / Linux', value: 'mac', }]}>
<TabItem value="windows">
```shell
.\gradlew.bat genesisStart -Pgenesis.start.headless=true -Pgenesis.start.restEnabled=true -Pgenesis.start.restPort=18080
```
</TabItem>
<TabItem value="mac">
```bash
./gradlew genesisStart -Pgenesis.start.headless=true -Pgenesis.start.restEnabled=true -Pgenesis.start.restPort=18080
```
</TabItem>
</Tabs>

:::important
The Gradle task doesn't enable the REST API unless you ask it to, so always pass `restEnabled=true`. The other `rest*` properties are ignored without it, so `restPort` on its own isn't enough, and Genesis Start exits straight away.
:::

See the [Gradle property reference](/develop/development-environment/genesis-start/configuration/#gradle-property-reference) for the other properties you can set.

The task starts Genesis Start in the background, then waits 5 seconds. If Genesis Start has already exited (for example, because it rejected an argument), the task fails and points you to `error.log` and `output.log`. Otherwise, it prints the process id and the addresses of the API documentation:

```
Genesis Start started with PID 12345
Swagger UI available on http://localhost:18080/api/docs
OpenApi spec available on http://localhost:18080/api/openapi.json
```

### Running the jar directly

For CI or other advanced uses, you can bypass Gradle completely and run the launcher jar yourself:

```bash
java -cp genesis-start-cp.jar global.genesis.launcher.app.MainKt \
  --root-project-path=/path/to/project --project=myproj \
  --task=projectOverviewBuilder --task-path=:projectOverviewBuilder \
  --outputs=/path/to/output.json \
  --headless --rest-port=18080
```

When you run the jar directly, the REST API is on by default, so `--headless` is enough, as long as you don't also pass `--no-rest`. The other REST flags are `--rest-base-path`, `--rest-api-version` and `--rest-max-body`. Add `--enable-experimental-features` to use experimental features, such as a non-zero [port offset](/develop/development-environment/genesis-start/configuration/#port-offset).

To pass database credentials without putting them on the command line, set the `GENESIS_LAUNCHER_DB_HOST`, `GENESIS_LAUNCHER_DB_USERNAME` and `GENESIS_LAUNCHER_DB_PASSWORD` environment variables instead of using `--db-host`, `--db-username` and `--db-password`. If you set both, the command-line flag wins. The names have a `GENESIS_LAUNCHER_` prefix so that a `DbPassword` variable already set in your shell isn't picked up by accident.

## Checking that it's running

When you use the start script or the Gradle task, Genesis Start writes its output to files rather than to your terminal. To follow them:

```bash
tail -f build/genesis-start/output.log
tail -f build/genesis-start/error.log
```

When Genesis Start is ready, you see:

```
Genesis <appName> is running in headless mode (no GUI window).
REST API listening at http://localhost:18080/api
```

To check that it's responding:

```bash
curl http://localhost:18080/api/health
```

## Driving it over REST

By default, the REST API listens on port **8080** under the path **`/api`** (for example, `http://localhost:8080/api/health`). You can change these with `restPort` and `restBasePath`. The examples on this page use port 18080.

The full reference, with request and response examples for each endpoint, is in the Swagger UI at `/api/docs`. The OpenAPI spec is at `/api/openapi.json`.

Here's a summary of the endpoints.

**Status**

| Endpoint | What it does |
|---|---|
| `GET /api/health` | Checks that Genesis Start is running. |
| `GET /api/status` | Shows the application's status, including whether a sync or other operation is in progress (`syncing`). |
| `GET /api/application-info` | Shows information about the application, including the project's `featureFlags`, whether `experimentalFeaturesEnabled` is on, and the current `portOffset` and `portMap`. |
| `GET /api/docs-url` | Returns a link to the Genesis Start documentation. |

**Processes**

| Endpoint | What it does |
|---|---|
| `GET /api/processes` | Lists the processes and their state. |
| `GET /api/processes/{processId}/info` | Shows details of one process, including its log file (`logFilePath`). |
| `POST /api/processes/{processId}/start` | Starts one process. |
| `POST /api/processes/{processId}/stop` | Stops one process. |
| `POST /api/processes/application/start-all` | Starts all stopped Application processes and the Web UI. Optional body: `{"skipSync": true}`. |
| `POST /api/processes/application/stop-all` | Stops all Application processes. This stops the processes, not Genesis Start. |
| `GET /api/processes/{processId}/log` | Reads a process's log. |
| `POST /api/processes/{processId}/log/clear` | Clears a process's log in Genesis Start. |
| `POST /api/processes/{processId}/input` | Sends a line to a utility's input. Body: `{"line": "..."}`. |

You can also start and stop a process with `POST /api/processes/start` and `POST /api/processes/stop`, giving the `processId` in the body.

**Bootstrap, sync, import and scripts**

| Endpoint | What it does |
|---|---|
| `POST /api/bootstrap` | Runs Bootstrap and Launch. Optional body: `{"skipSync": true}`. |
| `POST /api/sync` | Runs Sync Processes. |
| `POST /api/import` | Imports CSV files with `SendIt`. Body: `{"paths": [...]}`. |
| `GET /api/scripts` | Lists the scripts available for the current process profile. |
| `POST /api/scripts/run` | Runs a script. Body: `scriptId`, and optionally `arguments`, `workingDirectory` and `waitForExit`. |

Script arguments are split on spaces, with no support for quotes or escaping.

**Settings and profiles**

| Endpoint | What it does |
|---|---|
| `GET` or `PATCH /api/settings` | Reads or changes settings, such as Use Genesis Sync. |
| `GET` or `PATCH /api/preferences/view` | Reads or changes view preferences. |
| `GET` or `PUT /api/port-offset` | Reads or sets the [port offset](/develop/development-environment/genesis-start/configuration/#port-offset). |
| `GET /api/process-profiles` | Lists the [process profiles](/develop/development-environment/genesis-start/configuration/#process-profiles) and shows the current one. |
| `PUT /api/process-profiles/{profileId}` | Switches to another process profile. |

To switch profile, use an `id` from `GET /api/process-profiles`. Ids are case-sensitive, and an unknown id returns 404. After switching, call `GET /api/processes` and `GET /api/scripts` again, because both depend on the profile.

To put all routes under a version prefix (`/api/v1/...`), pass `--rest-api-version=v1` to the start script or the jar. There's no Gradle property for this.

### Long-running operations

Bootstrap, sync, start-all, import and script runs return straight away with an `operationId`. To follow the operation, call `GET /api/operations/{operationId}` until its `status` is `SUCCESS` or `FAILED`. If it failed, `message` explains why.

Only one bootstrap, sync or start-all can run at a time. If you start another while one is in progress, you get **409 Conflict**. You also get a 409 if you run a script or import files during a sync.

By default, a script run stays `RUNNING` until the script exits, then becomes `SUCCESS` if the exit code is 0 and `FAILED` otherwise. For scripts that keep running until you stop them, such as DbMon, pass `"waitForExit": false`. The operation then succeeds as soon as the script has started, and any later failure isn't reported on it.

### Process states

A process is in one of these states: `STOPPED`, `STARTING`, `RUNNING`, `HEALTHY`, `STOPPING` or `UNHEALTHY`. `RUNNING` means the process is up but hasn't reported its health yet; `HEALTHY` means it has reported itself healthy.

### Errors

Errors are returned as JSON, with a `code` (such as `NOT_FOUND`, `CONFLICT` or `VALIDATION_ERROR`), a `message` you can read, and sometimes `details`.

## Security

:::warning
The REST API has **no authentication**, and it listens on **all network interfaces**, not only `localhost`. You can't restrict it to `localhost`.
:::

Anyone who can reach the port can do everything the API allows: start and stop processes, run scripts with any arguments, import files from any path Genesis Start can read, send input to utilities, read logs and change settings. The same applies to the Swagger UI.

Keep the port local:

- On a laptop or desktop, make sure the port can't be reached from the network. A firewall on your machine is enough.
- On a remote development environment, don't open the port to the network. Connect through an SSH tunnel instead; for example, `ssh -L 18080:localhost:18080 devbox`, then use `http://localhost:18080/api` on your own machine.
- Don't run Genesis Start with the REST API enabled on a shared or untrusted network.

## Stopping it

There's no REST endpoint that shuts Genesis Start down. To stop it, press **Ctrl-C** if it's running in the foreground, or send it `SIGTERM`:

```bash
kill <pid>
```

Genesis Start logs `Shutdown requested, stopping headless launcher.`, stops the REST API, and stops all running processes (in the same order as [Stop All](/develop/development-environment/genesis-start/#start-all-and-stop-all)). It waits for all of this to finish, for up to about 34 seconds, which is long enough to force-kill any processes that ignore the request to stop. If any processes are still running after that, it exits anyway and logs a warning that names them.

To find the process id (`<pid>`):

- **Gradle task**: it is printed when Genesis Start starts (`Genesis Start started with PID 12345`).
- **Start script**: the script's process id is the same as Genesis Start's. Capture it when you start the script in the background: `build/genesis-start/start.sh & echo $!`
- If you've lost it, use `ps aux | grep MainKt`. This is ambiguous if more than one instance is running.
