|Software                            | Access Information                                                                      |

### LMDB installation guide (MacOS)

When running a Genesis application on MacOS, you must install and configure LMDB. The following steps can be followed:

1. Install lmdb for Mac: [homebrew installation instructions](https://formulae.brew.sh/formula/lmdb)
2. Add `liblmdb.dylib` to your Java Extensions:
```bash
mkdir -p ~/Library/Java/Extensions
cp /opt/homebrew/opt/lmdb/lib/liblmdb.dylib ~/Library/Java/Extensions/
```

## Gradle deploy plugin

The Genesis Application Platform provides a Gradle plugin that makes it easy to perform all the installation tasks that are necessary to deploy your own Genesis project on your local workstation, from your IDE.

The plugin is designed to work on workstations running Linux, or on WSL.

### Enabling the deployment plugin in your project

Simply set `genesisDeploy.enabled = true` in your application's `server/settings.gradle.kts` file.

```kotlin
  plugins {
    genesisDeploy.enabled = true
  }
```

#### General set-up

Make sure you have a `gradle.properties` file in the `.gradle` directory in your user home directory; this file must contain your Genesis Artifactory credentials in clear (unencrypted) text:

```shell
genesisArtifactoryUser=<your-artifactory-user>
genesisArtifactoryPassword=<your-artifactory-password>
```

:::note
This requires credentials for accessing Genesis Artifactory. If you have not been provided with the credentials, please contact your administrator, or [contact us](mailto:support@genesis.global?subject=Quick%20Start%20-%20Artifactory%20Login). It's not possible to complete the training without this access, because you won't be able to download the Genesis platform components and build your project.
:::

### Application Distribution

Applications can build zip distributions using the `appDistZip` Gradle task.

This Gradle task will create a standalone zip distribution for an application that can be deployed and that is used as input for the docker image process.

The zip file will include the full Genesis distribution, each PBC distribution, the app's server and web distribution.

There are two ways in which this zip can be constructed:
* By default, each Genesis dependency, including Genesis-Server and each PBC, will include its full set of jars. This non-dynamic mechanism is deprecated; see [Dynamic Deployments](#dynamic-deployments).
* If dynamic deployments are enabled, an App can take control of dependency resolution, and this will result in a single set of jars in `site-specific/lib`

### Dynamic Deployments

Using dynamic deployments, Apps can take control of dependency resolution, which achieves the following:
* Apps are able to overwrite vulnerable dependencies. It is the developer's responsibility to assess binary compatibility.
* A smaller distribution will be created, as jars are only included if required, and then only once.
* Each process's classpath is resolved and checked at build time, so a missing module or jar fails the build, or fails at `startProcess` with the names of the missing jars, instead of surfacing later as a `ClassNotFoundException`.

:::warning
Non-dynamic deployment (`enableDynamicDeployment=false`, still the default) is deprecated and will be removed in Genesis 11.0.0. Builds that use it log a deprecation warning. We recommend that all Genesis 10 applications enable dynamic deployments; follow [Migrating from non-dynamic deployments](#migrating-from-non-dynamic-deployments) below.
:::

#### Note on dynamic deployments and `-processes.templt.xml` files

When using dynamic deployments, process template files (`-processes.templt.xml`) are rendered at build time in order to construct the process classpaths.

At build time, the target environment is not yet known. As a result, environment-specific system definitions cannot be applied, and the resulting classpath is shared across all environments.

For this reason, the `module` and `classpath` tags should not be templated when using dynamic deployments.

#### Enabling Dynamic Deployments

To enable dynamic deployments you can either add a Gradle property in your site-side project's `gradle.properties`:

```properties
enableDynamicDeployment=true
```

Or set the same property in `genesisExec { ... }` in your `-app` or `-deploy` module.

```kotlin
genesisExec {
    enableDynamicDeployment = true
}
```

#### Migrating from non-dynamic deployments

1. Set `enableDynamicDeployment=true`, as shown in [Enabling Dynamic Deployments](#enabling-dynamic-deployments).

2. Build the distribution with `appDistZip` and check the build log for `written N process classpaths` and `written N module classpaths`. The build fails if a process that is started by default names a module or classpath item that none of the application's dependencies provide; with non-dynamic deployments, this was only found when the process was started.

3. Inspect the archive. With the default packaging, paths are under `server/`. `site-specific/lib` should hold the jars, `site-specific/modules/process` should hold one `.classpath` file per process, and `genesis/lib` should hold no jars.

4. Move anything that you used to add to the classpath by hand into Gradle dependencies (for example, using the [`genesisRuntime` configuration](#using-genesisruntime-configuration)). A dynamic classpath only lists what the build resolved, so:
   * jars copied by hand into `site-specific/lib` (or any other folder under `$GENESIS_HOME`) are not picked up
   * `GlobalClasspathAdditions` in the system definition is ignored
   * a JDBC driver is only on the classpath if your application depends on it; see [Declaring a JDBC driver](#declaring-a-jdbc-driver)

5. Deploy the new archive to a fresh `$GENESIS_HOME`, or replace the installation's `genesis` folder with the one from the archive. Then run `genesisInstall` and start the processes. If a jar is missing, `startProcess` fails with `classpath file ... references N missing JAR(s)` and names each missing jar.

#### Rolling back to non-dynamic deployments

1. Rebuild with `enableDynamicDeployment=false` and redeploy.
2. Remove the `site-specific/modules/process` folder from the installation. While that folder exists, the launcher scripts treat the installation as dynamic.

#### Known limitations

* **`GlobalClasspathAdditions`**: this system definition item is ignored under dynamic deployments. Declare each entry as a Gradle dependency instead.
* **Jars added by hand**: jars copied into `site-specific/lib` manually, rather than resolved by the build, are not on any process classpath. Declare them as Gradle dependencies instead.
* **OpenTelemetry Java Agent**: with [`OpenTelemetryJavaAgentEnabled`](/build-deploy-operate/operate/tracing/) set to `true`, the launcher adds `-javaagent:$GENESIS_HOME/genesis/lib/opentelemetry-javaagent.jar`, but dynamic deployments do not ship that jar. Until this is fixed, an application that uses the agent at runtime must supply that file itself. Running processes from the IDE or Gradle is not affected.

#### Using `genesisRuntime` configuration

To add runtime dependencies and set constraints, use the `genesisRuntime` configuration in Gradle.
Add these in `server/build.gradle.kts`.
For example, to add a runtime dependency on `javax.mail:mail:1.4` for all your processes, use:
```kotlin
dependencies {
    genesisRuntime("javax.mail:mail:1.4")
}
```

#### Declaring a JDBC driver

The Genesis database modules do not bring vendor JDBC drivers with them. Each deployment ships the driver for the database it uses, and nothing else.

| Deployment | What to do |
|---|---|
| Non-dynamic (`enableDynamicDeployment=false`) | Nothing. Every driver is still shipped in `genesis/lib`. |
| Dynamic (`enableDynamicDeployment=true`) | Declare the driver for your `DbHost`, as shown below. |

In a dynamic deployment, each process's classpath is built from its module's dependencies plus the [`genesisRuntime` configuration](#using-genesisruntime-configuration). Add the driver there, in the `dependencies { }` block of `server/build.gradle.kts` (the project that builds `appDistZip`). Leave the version out; the Genesis BOM supplies it.

:::warning
Declare the driver with `genesisRuntime`. A driver declared with `runtimeOnly` or `implementation` does not reach the process classpaths of a dynamic deployment.
:::

| Database | Declaration |
|---|---|
| PostgreSQL | `genesisRuntime("org.postgresql:postgresql")` |
| SQL Server | `genesisRuntime("com.microsoft.sqlserver:mssql-jdbc")` |
| Oracle | `genesisRuntime("com.oracle.database.jdbc:ojdbc11")` and `genesisRuntime("com.oracle.database.xml:xdb")`, each excluding `com.oracle.database.xml:xmlparserv2` (see the example below) |
| AWS Advanced JDBC Wrapper (`jdbc:aws-wrapper:…`) | `genesisRuntime("software.amazon.jdbc:aws-advanced-jdbc-wrapper")`, plus the driver for the database that it wraps |
| H2 | Nothing; H2 is always present |

For example, an application on PostgreSQL:

```kotlin
dependencies {
    genesisRuntime("org.postgresql:postgresql")
}
```

An application on Oracle:

```kotlin
dependencies {
    genesisRuntime("com.oracle.database.jdbc:ojdbc11") {
        exclude(group = "com.oracle.database.xml", module = "xmlparserv2")
    }
    genesisRuntime("com.oracle.database.xml:xdb") {
        exclude(group = "com.oracle.database.xml", module = "xmlparserv2")
    }
}
```

`genesisRuntime` reaches every module's classpath, including `genesisInstall`, remap and the console tools, so one declaration covers the whole deployment.

##### Other databases that your application connects to

`DbHost` is not the only database a deployment can reach. Declare a driver for every database engine that the following connect to:

* the [`DictionaryBuilder`](/build-deploy-operate/operate/commands/#dictionarybuilder), `DbToGenesis` and `GenesisToDb` tools, which read from or write to an external database
* external database sinks in data ingestion pipelines
* JDBC sources in [data pipelines](/develop/server-capabilities/integrations/data-pipelines/)

##### Tests

Tests that use `genesis-testsupport` get every driver at test runtime, so they run against any database engine without extra declarations.

Code that uses driver classes directly, such as `org.postgresql.util.PSQLException`, must declare the driver as an ordinary dependency (`implementation` or `compileOnly`), because it no longer arrives through the Genesis database modules.

##### When a driver is missing

A process whose `DbHost` driver is not on its classpath fails at start-up with a message that names the dependency and the declaration to add, for example:

```
No JDBC driver on the classpath for DbHost jdbc:postgresql. Add "org.postgresql:postgresql" to the process classpath; in a dynamic deployment, declare genesisRuntime("org.postgresql:postgresql").
```

The message shows only the engine part of the URL, never the full `DbHost`, so credentials in the URL are not logged.

#### Overwriting Dependency Vulnerabilities

The same configuration can be used for setting dependency constraints.
This is useful to patch the application, in case a vulnerability is detected, and waiting for the next Genesis release is not an option.
This can be done using the [standard Gradle constraint syntax](https://docs.gradle.org/current/userguide/dependency_constraints.html).
Care should be taken to test the application with the new dependency setup.
With every release of the Genesis platform, the platform is compiled and tested against its declared dependencies.
Overwriting dependencies can introduce subtle bugs and linkage errors.
Please read the release notes of the affected jars carefully for breaking changes.

#### Setting a minimum version

If a vulnerability exists in a dependency and a newer version without that vulnerability exists, the recommended approach is to set a minimum version.
This can be done using the `require()` syntax and adding a reason in `because()`.

For example, to set the minimum version of `netty-handler` to `4.1.100.Final` and add a reference to a CVE, use:
```kotlin
dependencies {
    constraints {
        genesisRuntime("io.netty:netty-handler") {
            version { require("4.1.100.Final") }
            because("CVE-2022-1471")
        }
    }
}
```

This will set the minimum version for the dependency across the application.
However, if after upgrading Genesis uses version `5.0.0`, Gradle will use that version.

#### When the only option is to roll back

Sometimes a vulnerability exists and the only option is to roll back until a fix is available.
In that case, you can use the same syntax:
```kotlin
constraints {
    genesisRuntime("com.example:problem-lib") {
        version { require("1.2.3") }
        because("CVE-2022-xxxx - rolling back 1.2.4–1.2.5 are broken; allow newer fixed releases")
    }
}
```

#### Overwriting using a BOM

In exceptional cases, a whole suite of dependencies might need to be overwritten.
In that case, if a library provides a BOM, you can use `enforcedPlatform`.
However, care should be taken to remove this overwrite once the platform is upgraded.

```kotlin
dependencies {
    // remove once Genesis platform version is upgraded
    // to cover CVE-2020-1234
    genesisRuntime(enforcedPlatform("com.fasterxml.jackson:jackson-bom:2.16.1"))
}
```

Please note that the same dependency resolution algorithm will be used when running a Genesis Application locally,
using the [IntelliJ plugin](/develop/development-environment/intellij-plugin) or [Genesis Start](/develop/development-environment/genesis-start).
